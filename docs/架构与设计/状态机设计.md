# 状态机设计

## 一、目的与范围

这份文档用于把《平台总导图》《项目确认记录》《核心表结构草图》中已经确认的运行态对象，进一步收敛成可以直接指导后端枚举、状态校验、接口约束和前端展示逻辑的状态机设计。

当前目标不是直接写代码，而是先明确：
- 哪些对象必须有清晰状态机
- 每个对象有哪些合法状态
- 什么动作会触发状态变化
- 哪些状态是终态
- 哪些状态允许撤回、重试、人工兜底

## 二、总原则

### 1. 统一原则
- 一个运行态对象只保留一个主状态字段
- 主状态表达“当前所处阶段”，动作历史由日志、事件、流水记录承担
- 不用多个布尔字段替代状态机

### 2. 终态原则
- 已完成、已驳回、已撤回、已取消、已解散、已离职等状态属于终态
- 终态默认不可逆
- 若业务上需要“恢复”，原则上走新流程、新任务、新版本，而不是直接回改旧状态

### 3. 人工兜底原则
- Agent、自动化任务、知识入库等异步过程都必须有失败态
- 高风险动作必须存在“等待人工确认”或“转人工处理”分支
- 系统超时、外部依赖异常、规则冲突，不允许默默吞掉，必须进入可追踪状态

### 4. 落库原则
- `org_user.employment_status` 负责员工主状态
- `wf_request.status` 负责业务申请主状态
- 审批任务状态由 Flowable 任务态 + `sys_todo_item.status` + `wf_task_action` 共同表达
- `att_exception.status` 负责考勤异常处理状态
- `im_conversation.status` / `im_group_profile.status` 负责会话与群组状态
- `agt_agent_version.publish_status`、`agt_task.status` 负责 Agent 发布态与运行态
- `kb_document.ingest_status`、`kb_ingest_job.status` 负责知识入库汇总态与任务态

## 三、员工生命周期状态机

### 1. 适用对象
- 主对象：`org_user.employment_status`
- 辅助对象：`hr_employee_event.status`

### 2. 主状态定义

| 中文状态 | 建议枚举值 | 含义 | 是否终态 |
| --- | --- | --- | --- |
| 待入职 | `PENDING_ONBOARD` | 人员档案已建立，尚未正式生效上岗 | 否 |
| 试用期 | `PROBATION` | 已入职，处于试用阶段 | 否 |
| 在职 | `ACTIVE` | 正常在职状态 | 否 |
| 待离职 | `PENDING_OFFBOARD` | 离职申请已通过或离职动作已发起，等待生效 | 否 |
| 已离职 | `OFFBOARDED` | 人员已完成离职，不再参与正常业务 | 是 |

### 3. 合法流转
- `待入职 -> 试用期`
  触发条件：入职流程通过，且存在试用期，入职生效日到达。
- `待入职 -> 在职`
  触发条件：入职流程通过，且无需试用期，入职生效日到达。
- `试用期 -> 在职`
  触发条件：转正流程通过并生效。
- `试用期 -> 待离职`
  触发条件：试用期离职或辞退流程通过。
- `在职 -> 待离职`
  触发条件：主动离职、辞退、退休等离场流程通过。
- `待离职 -> 离职前状态`
  触发条件：离职流程在生效前被撤销、驳回或作废。
  恢复目标不是固定写死为 `在职`，而是按离职前快照恢复为 `试用期` 或 `在职`。
- `待离职 -> 已离职`
  触发条件：离职生效时间到达且交接动作完成。

### 4. 例外处理
- `待入职` 阶段如果入职流程撤销或作废，第一版不单独增加“已取消入职”主状态。
  建议做法：不激活正式人员主档，不创建有效账号与业务附属关系，并通过 `hr_employee_event` 记录取消事件。
  如果该待入职档案后续不再使用，建议在后台以软删除或“仅归档可见”方式处理，避免形成大量僵尸待入职记录。
- `已离职` 不直接回退到 `在职`。
  返聘、重新入职必须走新一轮入职流程，可复用历史档案，但不能直接改旧状态回滚。

### 5. 生命周期事件状态

| 中文状态 | 建议枚举值 | 含义 |
| --- | --- | --- |
| 待生效 | `PENDING_EFFECTIVE` | 审批已通过，但异动尚未到生效时间 |
| 已生效 | `EFFECTIVE` | 已写入员工主档并完成联动 |
| 已取消 | `CANCELLED` | 生效前被撤销、作废或上游流程失效 |

### 6. 联动要求
- 入职生效时同步建立账号、考勤归属、假期账户初始化。
- 转正生效时可触发年假起算、额度发放、组织关系快照补录。
- 离职生效时同步关闭待办、停用登录、移出群组、冻结 Agent 直聊入口。

## 四、业务申请状态机

### 1. 适用对象
- 主对象：`wf_request.status`

### 2. 主状态定义

| 中文状态 | 建议枚举值 | 含义 | 是否终态 |
| --- | --- | --- | --- |
| 草稿 | `DRAFT` | 申请人已保存但未正式提交 | 否 |
| 待审批 | `PENDING_REVIEW` | 已提交，正处于系统预处理窗口，尚未进入稳定在途处理链路 | 否 |
| 审批中 | `IN_APPROVAL` | 已进入稳定在途处理阶段，可能包含人工审批、长耗时自动节点或持续等待链路 | 否 |
| 已通过 | `APPROVED` | 全部必经节点完成，流程通过 | 是 |
| 已驳回 | `REJECTED` | 任一驳回终止节点触发，流程结束 | 是 |
| 已撤回 | `WITHDRAWN` | 发起人在允许窗口内主动撤回 | 是 |

### 3. 合法流转
- `草稿 -> 待审批`
  触发条件：申请人提交成功，流程实例创建成功。
- `待审批 -> 审批中`
  触发条件：流程通过预处理窗口，进入稳定在途链路。
  典型场景包括：Agent 预审通过后转人工节点、进入需要等待或持续执行的自动节点、人工审批任务正式生成。
- `待审批 -> 已驳回`
  触发条件：首节点即被 Agent 硬规则驳回，或系统校验驳回。
- `待审批 -> 已撤回`
  触发条件：尚未产生首个实际处理动作前，发起人主动撤回。
- `审批中 -> 审批中`
  触发条件：正常流转、转审、加签、退回上一节点后继续处理、自动执行后进入下一节点。
- `审批中 -> 已通过`
  触发条件：最终通过节点完成。
- `审批中 -> 已驳回`
  触发条件：任一终止性驳回动作完成。
- `审批中 -> 已撤回`
  触发条件：业务规则允许撤回且当前节点支持撤回。

### 4. 状态判定口径
- `待审批` 强调“提交成功，但仍处于提交后预处理窗口”。
- 这个窗口允许非常短，也允许承载 Agent 预审这类首段自动处理。
- `审批中` 强调“已经进入稳定在途处理链路”，后续通常会出现人工节点、持续等待或多步自动执行。
- Agent 预审不单独升维成主状态，而是通过 `current_step_key/current_step_name` 与 `wf_task_action.agent_decision_json` 表达节点类型和预审结论。

### 5. 不可逆规则
- `已通过`、`已驳回`、`已撤回` 为终态。
- 终态后若业务需要重新申请，必须新建一条 `wf_request`。
- 不允许把“已驳回”直接改回“审批中”。

## 五、审批任务状态机

### 1. 适用对象
- 逻辑对象：审批节点任务
- 落地载体：Flowable 任务状态 + `sys_todo_item.status` + `wf_task_action`

### 2. 设计说明
- 第一版不强制新增独立业务任务主表。
- 但在业务语义上，审批任务仍然需要独立状态机，否则前端待办、批量审批、催办、超时升级会难以统一。

### 3. 逻辑状态定义

| 中文状态 | 建议枚举值 | 含义 | 是否终态 |
| --- | --- | --- | --- |
| 待处理 | `PENDING` | 节点已生成，等待候选人处理 | 否 |
| 处理中 | `PROCESSING` | 已被领取、已打开、或正在执行节点动作 | 否 |
| 已同意 | `APPROVED` | 当前节点处理人同意完成 | 是 |
| 已驳回 | `REJECTED` | 当前节点处理人驳回完成 | 是 |
| 已退回 | `RETURNED` | 退回上一节点或退回发起人 | 是 |
| 已转交 | `TRANSFERRED` | 当前节点已转交他人处理 | 是 |
| 已撤销 | `CANCELLED` | 上游流程撤回或结束，当前任务失效 | 是 |
| 已超时关闭 | `TIMEOUT_CLOSED` | 超时后被系统关闭或升级替代 | 是 |

### 4. 合法流转
- `待处理 -> 处理中`
  触发条件：处理人领取、打开并开始处理，或系统进入正在执行。
- `待处理 -> 已同意`
  触发条件：无需显式领取，直接审批通过。
- `待处理 -> 已驳回`
  触发条件：无需显式领取，直接审批驳回。
- `待处理 -> 已转交`
  触发条件：当前处理人转审给他人。
- `待处理 -> 已撤销`
  触发条件：上游流程撤回、终止、被前置节点拦截。
- `待处理 -> 已超时关闭`
  触发条件：超时策略直接关闭该任务。
- `处理中 -> 已同意`
  触发条件：处理完成并同意。
- `处理中 -> 已驳回`
  触发条件：处理完成并驳回。
- `处理中 -> 已退回`
  触发条件：退回上一节点或发起人。
- `处理中 -> 已转交`
  触发条件：处理中转审。
- `处理中 -> 已撤销`
  触发条件：流程被外部动作终止。

### 5. 额外规则
- 会签节点下，一个人的任务终态不代表整个节点终态。
- 任意一人通过型节点，满足规则后其余同级任务应进入 `已撤销`。
- 催办不改变任务状态，只追加 `wf_urge_record`。

## 六、考勤异常状态机

### 1. 适用对象
- 主对象：`att_exception.status`

### 2. 主状态定义

| 中文状态 | 建议枚举值 | 含义 | 是否终态 |
| --- | --- | --- | --- |
| 待处理 | `PENDING` | 已识别到异常，尚未进入修正链路 | 否 |
| 处理中 | `PROCESSING` | 已发起补卡、审核或人工修正 | 否 |
| 已修正 | `RESOLVED` | 异常已通过补卡、规则修正或人工确认解决 | 是 |
| 已忽略 | `IGNORED` | 明确认定无需修正 | 是 |
| 已关闭 | `CLOSED` | 因窗口过期、人员离职等原因关闭 | 是 |

### 3. 合法流转
- `待处理 -> 处理中`
  触发条件：员工发起补卡申请，或考勤管理员开始处理。
- `处理中 -> 已修正`
  触发条件：补卡审批通过并回写考勤结果，或人工修正完成。
- `处理中 -> 已忽略`
  触发条件：管理员认定该异常无需处理。
- `待处理 -> 已关闭`
  触发条件：超过处理窗口仍无人处理。
- `处理中 -> 已关闭`
  触发条件：关联流程作废、用户离职、业务窗口关闭。

### 4. 联动要求
- `已修正` 时必须回写 `att_daily_result`。
- 若由补卡申请解决，`resolved_request_id` 必须指向对应 `wf_request.id`。

## 七、会话与群组状态机

### 1. 适用对象
- 会话主对象：`im_conversation.status`
- 群组扩展对象：`im_group_profile.status`

### 2. 会话主状态定义

| 中文状态 | 建议枚举值 | 含义 | 是否终态 |
| --- | --- | --- | --- |
| 正常 | `ACTIVE` | 会话可继续收发消息 | 否 |
| 已归档 | `ARCHIVED` | 会话不再作为活跃入口，但历史仍可查看 | 否 |
| 已关闭 | `CLOSED` | 会话被系统关闭，不再允许继续写入 | 是 |

### 3. 群组扩展状态定义

| 中文状态 | 建议枚举值 | 含义 | 是否终态 |
| --- | --- | --- | --- |
| 正常 | `ACTIVE` | 群组可正常管理和发言 | 否 |
| 已归档 | `ARCHIVED` | 群组保留历史，不再作为活跃协同容器 | 否 |
| 已解散 | `DISSOLVED` | 群组终止，成员关系冻结 | 是 |

### 4. 合法流转
- `正常 -> 已归档`
  触发条件：群主/管理员主动归档，或绑定业务对象结束后自动归档。
- `已归档 -> 正常`
  触发条件：群组重新启用，或绑定业务对象重新激活。
- `正常 -> 已解散`
  触发条件：群主解散、自定义群治理关闭、组织群对应组织停用且策略要求同步关闭。
- `已归档 -> 已解散`
  触发条件：归档后确认不再保留为可恢复协同容器。

### 5. 约束说明
- “全员禁言”不作为主状态，属于 `speak_mode` 配置。
- “自动同步成员”不作为主状态，属于 `auto_sync_mode` 配置。
- 私聊与 Agent 直聊原则上不支持“解散”，仅支持归档或关闭。

## 八、Agent 发布态与任务态状态机

### 1. Agent 版本发布状态

#### 适用对象
- 主对象：`agt_agent_version.publish_status`

#### 状态定义

| 中文状态 | 建议枚举值 | 含义 | 是否终态 |
| --- | --- | --- | --- |
| 草稿 | `DRAFT` | 管理员正在编辑配置 | 否 |
| 测试中 | `TESTING` | 仅测试环境或测试人员可用 | 否 |
| 已发布 | `PUBLISHED` | 对授权用户正式可用 | 否 |
| 已停用 | `DISABLED` | 已下线，不再新建任务 | 否 |
| 已归档 | `ARCHIVED` | 仅保留历史版本，不再恢复使用 | 是 |

#### 合法流转
- `草稿 -> 测试中`
  触发条件：管理员发起联调、沙箱测试或小范围试运行。
- `测试中 -> 已发布`
  触发条件：测试通过，管理员正式发布。
- `已发布 -> 已停用`
  触发条件：管理员停用，或发现重大风险紧急下线。
- `已停用 -> 测试中`
  触发条件：修复后重新进入验证阶段。
- `已停用 -> 已归档`
  触发条件：确认版本废弃，不再复用。

#### 额外规则
- 同一 `agt_agent` 在同一时刻只能有一个 `published_version_id` 指向的正式发布版本。
- 回滚不是独立稳定状态。
  建议做法：把旧版本重新置为 `已发布`，把当前版本置为 `已停用` 或 `已归档`。

### 2. Agent 任务运行状态

#### 适用对象
- 主对象：`agt_task.status`

#### 状态定义

| 中文状态 | 建议枚举值 | 含义 | 是否终态 |
| --- | --- | --- | --- |
| 待执行 | `PENDING` | 任务已创建，等待调度执行 | 否 |
| 执行中 | `RUNNING` | 模型推理、工具调用或工作流节点执行中 | 否 |
| 等待人工确认 | `WAITING_HUMAN_CONFIRM` | 命中高风险写操作、低置信度结果或策略要求转人工 | 否 |
| 已完成 | `SUCCEEDED` | 任务已成功产出最终结果 | 是 |
| 已驳回 | `REJECTED` | 规则明确不允许继续执行，或人工拒绝继续 | 是 |
| 执行失败 | `FAILED` | 外部依赖、模型、工具、参数或系统异常导致失败 | 是 |
| 已取消 | `CANCELLED` | 上游取消、会话关闭、流程终止或管理员停止任务 | 是 |

#### 合法流转
- `待执行 -> 执行中`
  触发条件：调度器取到任务开始执行。
- `执行中 -> 已完成`
  触发条件：模型输出成功，工具调用完成，任务结果已落库。
- `执行中 -> 等待人工确认`
  触发条件：命中高风险工具、需要审批确认、或置信度不足。
- `等待人工确认 -> 执行中`
  触发条件：人工同意继续，由系统恢复任务。
- `等待人工确认 -> 已驳回`
  触发条件：人工拒绝继续执行。
- `等待人工确认 -> 已取消`
  触发条件：等待超过确认时限，或确认人失效、会话关闭、上游上下文被终止。
- `执行中 -> 执行失败`
  触发条件：重试耗尽或不可恢复异常发生。
- `待执行 -> 已取消`
  触发条件：任务尚未执行即被取消。
- `执行中 -> 已取消`
  触发条件：管理员中止、上游流程终止、关联上下文失效。
- `执行中 -> 已驳回`
  触发条件：规则校验不通过，且该任务设计为直接驳回型结论。

#### 额外规则
- 只读问答型 Agent 一般不会进入 `等待人工确认`，而是直接 `已完成` 或 `执行失败`。
- 流程预审型 Agent 可以直接输出 `已驳回`，但必须写审计日志。
- `执行失败` 后是否允许重试，不由状态机决定，而由任务策略决定；重试建议创建新尝试记录，不直接抹掉失败事实。
- `等待人工确认` 必须有超时策略，建议默认 72 小时，可按 Agent 或工具风险等级配置。
- 超时后至少执行两件事：
  1. 任务流转到 `已取消` 或按策略升级到新的人工处理人
  2. 写入 `agt_audit_log` 和提醒事件，避免任务永久挂起

## 九、知识入库状态机

### 1. 知识文档入库汇总状态

#### 适用对象
- 主对象：`kb_document.ingest_status`

#### 状态定义

| 中文状态 | 建议枚举值 | 含义 | 是否终态 |
| --- | --- | --- | --- |
| 未入库 | `NOT_INGESTED` | 仅有主记录，尚未进入入库链路 | 否 |
| 待入库 | `PENDING` | 已提交入库任务，等待执行 | 否 |
| 入库中 | `PROCESSING` | 有任务正在解析、切片、向量化或写索引 | 否 |
| 已可用 | `READY` | 当前版本索引可供检索使用 | 否 |
| 入库失败 | `FAILED` | 最近一次入库失败，当前无可用新版本 | 否 |
| 已下线 | `OFFLINE` | 知识文档被禁用或撤下，不参与检索 | 是 |

#### 合法流转
- `未入库 -> 待入库`
  触发条件：创建入库任务。
- `待入库 -> 入库中`
  触发条件：任务开始执行。
- `入库中 -> 已可用`
  触发条件：切片、向量化、索引写入全部成功。
- `入库中 -> 入库失败`
  触发条件：任一关键步骤失败且未恢复。
- `入库失败 -> 待入库`
  触发条件：重新发起入库。
- `已可用 -> 待入库`
  触发条件：文档内容更新，需要重新入库。
- `已可用 -> 已下线`
  触发条件：文档被禁用、删除或失去知识使用资格。

#### 安全口径
- 第一版建议采用“安全优先”而不是“陈旧可用优先”。
- 如果知识源内容已经变更，且重新入库失败，`kb_document.ingest_status` 应标记为 `FAILED`，并建议暂停对外检索，避免 RAG 返回过期内容。
- 检索层应只查询当前激活切片集合，例如过滤 `kb_vector_chunk.is_active=true`。
- 当文档从 `READY` 转为 `FAILED` 或 `OFFLINE` 时，应同步切换切片可检索状态，而不是只改 MySQL 汇总态。

### 2. 知识入库任务状态

#### 适用对象
- 主对象：`kb_ingest_job.status`

#### 状态定义

| 中文状态 | 建议枚举值 | 含义 | 是否终态 |
| --- | --- | --- | --- |
| 待执行 | `PENDING` | 任务已排队 | 否 |
| 解析中 | `PARSING` | 正在解析文档或抽取正文 | 否 |
| 切片中 | `CHUNKING` | 正在进行文本切片 | 否 |
| 向量化中 | `EMBEDDING` | 正在调用 embedding 模型生成向量 | 否 |
| 索引写入中 | `INDEXING` | 正在写入 PostgreSQL 向量表与映射关系 | 否 |
| 已完成 | `SUCCEEDED` | 入库任务成功结束 | 是 |
| 已失败 | `FAILED` | 任务失败 | 是 |
| 已取消 | `CANCELLED` | 任务被手工取消或被更新任务替代 | 是 |

#### 合法流转
- `待执行 -> 解析中 -> 切片中 -> 向量化中 -> 索引写入中 -> 已完成`
- 任一中间态都可以因为不可恢复异常进入 `已失败`
- `待执行` 或任一中间态都可以因为管理员取消、重复任务替换进入 `已取消`

#### 额外规则
- `kb_chunk_manifest` 只记录成功落账的切片映射，不记录还没真正入索引的中间临时切片。
- 若要支持增量重建，建议以新 `kb_ingest_job` 覆盖旧结果，而不是复用旧任务状态反复跳转。
- 同一 `kb_document` 在同一时刻只允许存在一个活动中的入库任务，避免并发重建导致向量结果冲突。

## 十、模板版本状态机

### 1. 适用对象
- 主对象：`wf_template_version.status`

### 2. 主状态定义

| 中文状态 | 建议枚举值 | 含义 | 是否终态 |
| --- | --- | --- | --- |
| 草稿 | `DRAFT` | 模板编辑中，未进入正式生效链路 | 否 |
| 待生效 | `PENDING_EFFECTIVE` | 已发布但未到生效时间 | 否 |
| 生效中 | `EFFECTIVE` | 当前版本可供新流程发起使用 | 否 |
| 已失效 | `EXPIRED` | 已过生效窗口，不再用于新流程 | 否 |
| 已停用 | `DISABLED` | 管理员手工停用 | 否 |

### 3. 合法流转
- `草稿 -> 待生效`
  触发条件：管理员发布模板版本，并设置未来生效时间。
- `草稿 -> 生效中`
  触发条件：管理员发布模板版本，并立即生效。
- `待生效 -> 生效中`
  触发条件：到达生效时间。
- `生效中 -> 已失效`
  触发条件：到达 `effective_to`，或被新版本接替后过期。
- `待生效 -> 已停用`
  触发条件：生效前取消发布。
- `生效中 -> 已停用`
  触发条件：紧急停用，不允许新流程继续引用。
- `已停用 -> 待生效`
  触发条件：管理员重新启用该版本，并设置未来生效时间。
- `已停用 -> 生效中`
  触发条件：管理员重新启用该版本，并要求立即生效。

### 4. 额外规则
- 在途流程仍然绑定发起时的模板版本，不受后续停用或新版本替换影响。
- 同一模板在同一时间点应只有一个“生效中”的主用版本。
