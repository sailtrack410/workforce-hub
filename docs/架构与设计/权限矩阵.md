# 权限矩阵

## 一、目的与范围

这份文档用于把《平台总导图》《项目确认记录》《核心表结构草图》《状态机设计》中已经确认的角色边界，进一步收敛成第一版可开发、可校验、可审计的权限矩阵。

当前目标不是穷举所有按钮，而是先明确：
- 哪些主体参与权限判断
- 权限判断分哪几层
- 不同主体默认能进哪些模块
- 不同主体能看什么、能做什么
- Agent 的可见、可用、可执行边界是什么

## 二、设计前提

### 1. 身份主体
- 员工
- 领导
- 管理员
- Agent

### 2. 基本原则
- 领导不是后台管理员，而是员工增强身份
- 管理员不默认进入业务协同会话
- Agent 不是人类账号，不继承人类自然身份
- 第一版采用“固定规则 + 明确授权”模式，不做难以解释的动态表达式权限系统

### 3. 权限总公式
- 人类用户最终权限 = 身份基础权限 ∩ 组织数据范围 ∩ 业务对象状态约束
- Agent 最终权限 = Agent 自身授权 ∩ 触发主体可见范围 ∩ 当前业务场景范围

## 三、权限分层模型

### 1. 模块准入权限
- 能不能进入某个产品域或页面域
- 例如：能不能进入消息、待办、审批、后台治理、Agent 管理

### 2. 操作权限
- 能不能执行某个动作
- 例如：发起申请、审批通过、建群、发布 Agent、重新入库知识文档

### 3. 数据范围权限
- 能看到哪些数据
- 例如：仅自己、自己团队、自己参与的会话、被授权文档、全局治理数据

### 4. 工具与系统权限
- 主要用于 Agent、管理员治理、外部连接器调用
- 例如：能否调用余额校验工具、能否读取知识库、能否触发外部系统写入

## 四、主体定义与默认能力

### 1. 员工
- 默认进入 `employee-web`
- 默认可访问：消息、待办、文档、工作台、我的、个人考勤、个人假期、个人申请
- 默认数据范围：仅自己 + 自己参与的协同对象

### 2. 领导
- 默认进入 `employee-web`
- 拥有员工全部基础能力
- 额外拥有：团队审批、团队查看、团队排班、团队异常处理等能力
- 默认数据范围：自己 + 管理范围

### 3. 管理员
- 默认进入 `admin-web`
- 负责组织、流程、规则、群组治理、Agent、知识库、连接器、审计等后台能力
- 默认数据范围：全局治理数据
- 不默认拥有员工端协同会话内容查看权

### 4. Agent
- 不登录 `employee-web` 或 `admin-web`
- 通过会话、流程、任务、定时器、事件规则参与业务
- 是否可被发现、可被使用、可自动执行，均由后台单独授权

## 六、数据范围矩阵

### 1. 通用范围定义

| 范围级别 | 含义 |
| --- | --- |
| SELF | 仅自己 |
| PARTICIPATED | 自己参与的对象 |
| TEAM | 自己及管理范围 |
| GLOBAL_GOVERNANCE | 全局治理数据 |
| CONTEXT_INTERSECTION | 授权范围与上下文交集 |

### 2. 业务数据范围

| 数据域 | 员工 | 领导 | 管理员 | Agent |
| --- | --- | --- | --- | --- |
| 员工基本资料 | `SELF` | `TEAM` 只限业务需要字段 | `GLOBAL_GOVERNANCE` | `CONTEXT_INTERSECTION` |
| 组织架构 | 可见自己所在链路 | 可见自己管理链路 | `GLOBAL_GOVERNANCE` | `CONTEXT_INTERSECTION` |
| 考勤记录 | `SELF` | `TEAM` | `GLOBAL_GOVERNANCE` | `CONTEXT_INTERSECTION` |
| 假期余额 | `SELF` | `TEAM` | `GLOBAL_GOVERNANCE` | `CONTEXT_INTERSECTION` |
| 业务申请 | 自己发起、参与审批、被抄送 | 自己 + 团队相关 | `GLOBAL_GOVERNANCE` | `CONTEXT_INTERSECTION` |
| 文档 | 被授权文档 | 被授权文档 + 团队协作文档 | 仅治理元数据默认全局 | `CONTEXT_INTERSECTION` |
| 知识库 | 被授权空间 | 被授权空间 | 治理与配置全局 | 仅绑定空间 + 上下文允许范围 |
| 私聊会话 | 自己参与的会话 | 自己参与的会话 | 默认不可见内容 | 仅授权进入的会话 |
| 群聊会话 | 自己加入的群 | 自己加入的群 | 默认不可见内容 | 仅授权进入的群 |
| 审计日志 | 个人可见自己的部分结果 | 团队相关结果有限可见 | `GLOBAL_GOVERNANCE` | 仅自身执行日志 |

### 3. 领导管理范围口径
- 第一版以 `org_user.manager_user_id` 和 `org_department.tree_path` 共同确定管理范围。
- 优先口径：
  - 审批类：按审批规则实际命中的候选范围
  - 团队数据类：自己直属及间接下级，且落在自己管理组织链路内
  - 协同会话类：不因为是领导就自动获得团队成员私聊查看权

### 4. 管理员数据范围口径
- 管理员拥有治理数据全局权限。
- 管理员不默认拥有员工业务会话内容、员工私人文档内容、无授权知识空间内容。
- 管理员若因审计需要访问敏感内容，建议走显式审计动作，并记录原因与操作日志。

## 八、会话与群组权限规则

### 1. 私聊准入规则
- 员工可向直属上级发起私聊
- 员工可向直属下级发起私聊
- 员工可向同群成员发起私聊
- 不因同部门自动开放私聊
- 不因领导身份自动开放任意员工私聊
- 第一版默认采用严格准入策略
- 如后续需要放宽，建议通过系统参数扩展为可配置策略，而不是直接改核心权限代码

### 2. 群组规则
- 群组分为：组织群、业务群、自定义群
- 组织群成员由组织关系和同步策略决定
- 业务群成员由绑定业务对象和业务规则决定
- 自定义群成员由群主/管理员按策略维护

### 3. 管理员治理边界
- 管理员可治理群组存在性、成员策略、命名规范、违规处理
- 管理员不默认读取群消息内容
- 如发生审计场景，建议走显式审计入口并记录 `sys_audit_log`

### 4. Agent 会话边界
- Agent 只能进入授权会话
- Agent 在会话中只拥有被授予的消息发送、上下文读取、工具调用能力
- Agent 不因为被绑定到某个会话就自动拥有会话相关所有业务数据

## 十、Agent 工具权限矩阵

### 1. 风险等级定义

| 风险等级 | 典型示例 | 第一版默认策略 |
| --- | --- | --- |
| 只读 | 查余额、查组织、查知识、查流程状态 | 允许自动执行 |
| 低风险写入 | 发提醒、发系统消息、写任务备注 | 允许受控自动执行 |
| 中风险写入 | 创建草稿、发起低风险系统动作 | 需要明确 `approval_mode` |
| 高风险写入 | 改余额、改组织、直接终审、外部系统落单 | 默认不自动执行 |

### 2. 执行规则
- Agent 工具调用前必须同时满足：
  - Agent 版本已发布且未停用
  - Agent 具备该工具授权
  - 当前触发主体具备相关数据可见范围
  - 当前上下文允许该动作发生
- 第一版工具实现形态限定为：
  - 内部受控查询 / 回调 SPI
  - 通过连接器封装的 HTTP 工具
- 第一版不支持用户自定义脚本、动态代码片段或任意 JVM 方法直接作为 Agent 工具执行
- 命中高风险写操作时：
  - 进入 `WAITING_HUMAN_CONFIRM`
  - 或直接拒绝执行
- Agent 不能直接查看明文凭证
- 外部系统调用必须经由连接器和工具封装执行
- Prompt 只负责提出调用意图，真正是否允许执行必须由工具层再次校验，不能信任模型自身的“理解”

## 十一、后台治理权限拆分建议

为了避免“超级管理员一个角色包打天下”，第一版后台建议至少拆成以下角色层：
- 组织管理员
  - 管组织、人员、岗位、直属上级
- 流程管理员
  - 管模板、版本、审批规则、委托规则
- 考勤管理员
  - 管考勤组、班次、工作日历、异常处理
- 知识库管理员
  - 管知识空间、入库任务、知识权限
- Agent 管理员
  - 管 Agent、工具授权、触发器、发布停用
- 系统管理员
  - 管连接器、凭证元数据、系统参数、审计

### 说明
- 一个后台用户可以同时拥有多个治理角色。
- 后台角色用于 `admin_*` 体系，不进入业务组织树。

## 十二、第一版后端落地建议

### 1. 判定顺序
- 先判定身份主体
- 再判定入口模块
- 再判定业务动作
- 再判定数据范围
- 最后判定状态机是否允许当前动作

### 2. 权限拒绝返回口径
- 无登录态：`401`
- 有登录态但无模块 / 动作权限：`403`
- 有权限但目标数据不在范围内：`403`
- 有权限且数据在范围内，但对象状态不允许：`409`

### 3. 不建议做法
- 不把领导权限简单等同于“管理员弱化版”
- 不把管理员权限简单等同于“全能查看一切内容”
- 不把 Agent 权限设计成只看工具授权，不看触发主体和上下文
