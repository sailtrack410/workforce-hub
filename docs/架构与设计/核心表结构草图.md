# 核心表结构草图

## 一、目的与范围

这份文档用于把《平台总导图》和《项目确认记录》落成第一版核心数据结构草图。

当前目标不是直接生成 SQL，而是先确定：
- 核心表有哪些
- 各表职责是什么
- 关键字段应该放哪里
- 表与表之间如何关联
- 哪些数据放 MySQL，哪些数据放 PostgreSQL，哪些数据放 Redis

## 二、设计前提

### 1. 部署与租户前提
- 系统采用单客户独立部署
- 单实例单企业
- 第一版不引入平台级 `tenant_id`
- 分公司、子公司按组织体系建模，不抽象为租户

### 2. 身份前提
- 员工、领导共用一套业务用户体系
- 管理员为独立后台账号体系
- Agent 为系统身份，不属于人类账号

### 3. 技术前提
- 主业务库：MySQL
- 向量检索库：PostgreSQL + pgvector
- 缓存与会话：Redis
- 审批流引擎：Flowable

### 4. 结构前提
- 第一版优先“强业务可读性”，不追求过度抽象
- 审批类业务采用“公共流程头 + 业务明细表”模式
- 知识库向量数据不是业务真相源，MySQL 中的知识文档主记录才是业务真相源

## 三、存储边界

## 1. MySQL 承担的内容
- 组织、人员、账号、权限
- 考勤、排班、假期、工龄
- 审批模板、业务申请、审批动作
- 会话、群组、消息元数据
- Agent 配置、任务、审计
- 知识文档主记录、入库任务、权限
- 连接器、凭证元数据、附件元数据

## 2. PostgreSQL 承担的内容
- 知识切片
- embedding 向量
- 相似度检索索引
- RAG 检索用元数据副本

## 3. Redis 承担的内容
- 登录会话
- 邮箱验证码
- 幂等键
- 限流键
- 高频缓存
- 短期任务状态

## 4. 不在本文展开的内容
- Flowable 引擎内置表
- Redis key 设计
- 搜索引擎索引设计
- 监控指标存储设计

## 四、通用建模约定

### 1. 命名约定
- 表名前缀按业务域划分：
  - `org_` 组织与人员
  - `auth_` 业务账号认证
  - `admin_` 后台账号与 RBAC
  - `att_` 考勤与排班
  - `lv_` 假期与余额
  - `wf_` 流程与审批
  - `im_` 会话与群组
  - `doc_` 文档
  - `kb_` 知识库
  - `agt_` Agent
  - `sys_` 平台共享能力

### 2. 主键约定
- MySQL 主键统一使用 `BIGINT`
- PostgreSQL 向量表主键可使用 `BIGINT`
- 业务唯一编码单独使用 `code` 或 `*_no` 字段，不用字符串做主键

### 3. 通用字段约定
多数 MySQL 业务表建议统一具备以下字段：
- `id`
- `created_at`
- `updated_at`
- `created_by`
- `updated_by`
- `is_deleted`

运行态/日志类表可按需要去掉 `is_deleted`，改为只追加不删除。

### 4. 状态字段约定
- 所有运行态对象显式保留 `status`
- 不用“是否完成”“是否有效”等多个布尔字段替代状态机

### 5. 快照约定
以下场景要保留快照，而不是只靠实时关联：
- 审批发起时的申请人部门、岗位、直属上级
- 审批节点的候选人和实际处理人
- 员工异动前后组织关系
- 假期扣减与发放时的规则口径

## 五、组织、人员与认证

### 1. `org_department`
- 用途：组织树主表，承载总公司、分公司、部门、班组等组织节点
- 关键字段：
  - `id`
  - `parent_id`
  - `tree_path`
  - `dept_code`
  - `dept_name`
  - `dept_type`
  - `dept_level`
  - `leader_user_id`
  - `status`
- 说明：
  - `leader_user_id` 表示组织意义上的第一负责人
  - 分公司、子公司通过 `dept_type` 区分，不单独建租户表
  - `tree_path` 用于快速做子树查询、数据范围判定、组织群同步等场景

### 2. `org_position`
- 用途：岗位/职务定义
- 关键字段：
  - `id`
  - `position_code`
  - `position_name`
  - `position_category`
  - `status`

### 3. `org_user`
- 用途：员工/领导业务主表
- 关键字段：
  - `id`
  - `employee_no`
  - `real_name`
  - `gender`
  - `mobile`
  - `primary_dept_id`
  - `position_id`
  - `manager_user_id`
  - `employment_status`
  - `hire_date`
  - `regularized_at`
  - `service_start_date`
  - `annual_leave_start_date`
  - `work_location`
  - `status`
- 说明：
  - `manager_user_id` 表示当前直属上级
  - 领导身份不在此表单独建角色字段，而由组织关系和领导表共同决定
  - `employment_status` 建议覆盖：待入职、试用期、在职、待离职、已离职

### 4. `org_department_leader`
- 用途：部门领导成员表，支持一个部门多个领导成员
- 关键字段：
  - `id`
  - `dept_id`
  - `user_id`
  - `leader_type`
  - `is_primary`
  - `sort_order`
  - `status`
- 说明：
  - `leader_type` 可取：正职、副职、代理负责人等
  - 用于审批候选解析、团队管理范围参考

### 5. `auth_user_account`
- 用途：业务用户登录账号表
- 关键字段：
  - `id`
  - `user_id`
  - `login_name`
  - `password_hash`
  - `password_salt`
  - `email`
  - `email_verified_at`
  - `account_status`
  - `last_login_at`
  - `password_updated_at`
- 说明：
  - 员工与领导共用这套账号
  - 邮箱验证码存 Redis，不单独设计数据库主表

### 6. `admin_user`
- 用途：后台管理员账号表
- 关键字段：
  - `id`
  - `username`
  - `password_hash`
  - `password_salt`
  - `display_name`
  - `email`
  - `status`
  - `last_login_at`
- 说明：
  - 管理员独立于业务用户体系
  - 即使现实中是同一个人，也不与 `org_user` 共用账号记录

### 7. `admin_role`

- 关键字段：

### 8. `admin_permission`

### 10. `admin_role_permission`

- 说明：
  - 用于把 MySQL 中的文档主记录和 PostgreSQL 中的向量行建立映射
  - 入库写入顺序建议为：先写 PostgreSQL `kb_vector_chunk`，成功后再写 MySQL `kb_chunk_manifest`
  - 如果 PostgreSQL 已写成功但 MySQL 总账写入失败，应把该批向量标记为待清理孤儿数据，不能直接把 `kb_document.ingest_status` 置为 `READY`

### 10. `kb_vector_chunk`
- 所在库：PostgreSQL
- 用途：向量检索主表
- 关键字段：
  - `id`
  - `kb_document_id`
  - `space_id`
  - `ingest_job_id`
  - `chunk_no`
  - `chunk_text`
  - `embedding`
  - `metadata_json`
  - `content_hash`
  - `is_active`
- 说明：
  - `embedding` 使用 pgvector
  - 该表用于检索，不作为业务真相源
  - 检索查询必须只命中 `is_active=true` 的切片
  - 当知识文档重建失败或被下线时，需要切换或关闭旧切片的可检索状态
  - 同一知识文档允许保留多次入库历史，因此切片唯一性应按 `ingest_job_id + chunk_no` 控制，而不是只按 `kb_document_id + chunk_no`

## 八、会话、群组与消息

### 1. `im_conversation`
- 用途：统一会话主表
- 关键字段：
  - `id`
  - `conversation_type`
  - `conversation_key`
  - `title`
  - `avatar_file_id`
  - `bound_agent_id`
  - `last_message_seq`
  - `last_message_id`
  - `last_message_at`
  - `status`
- 说明：
  - `conversation_type` 支持：私聊、群聊、Agent 会话
  - Agent 直聊会话通过 `bound_agent_id` 绑定
  - `conversation_key` 只用于约束私聊/Agent 直聊唯一性，群聊可为空
  - 私聊 `conversation_key` 建议按成员 ID 排序生成，例如 `private:user:12:user:34`
  - Agent 直聊 `conversation_key` 建议按用户与 Agent 生成，例如 `agent:user:12:agent:7`
  - 即使是 Agent 直聊，也仍建议在 `im_conversation_member` 中写入用户和 Agent 两类成员
  - `seq_no` 不应通过 `MAX(seq_no)+1` 生成，建议通过 Redis 原子递增或基于 `last_message_seq` 的行级更新分配

### 2. `im_conversation_member`
- 用途：会话成员表
- 关键字段：
  - `id`
  - `conversation_id`
  - `member_type`
  - `member_id`
  - `member_role`
  - `join_source`
  - `mute_flag`
  - `pin_flag`
  - `last_read_seq`
  - `joined_at`
  - `left_at`
  - `status`
- 说明：
  - 群主/群管理员/成员均通过 `member_role` 表示
  - 私聊也使用该表表示两方成员

### 3. `im_group_profile`
- 用途：群组扩展信息，仅群聊类型会话使用
- 关键字段：
  - `id`
  - `conversation_id`
  - `group_type`
  - `binding_object_type`
  - `binding_object_id`
  - `owner_user_id`
  - `history_visible_mode`
  - `speak_mode`
  - `auto_sync_mode`
  - `notice_text`
  - `status`
- 说明：
  - `group_type` 支持：组织群、业务群、自定义群
  - 组织群可绑定 `org_department`，业务群可绑定流程、任务、项目等业务对象
  - `auto_sync_mode` 只描述是否自动同步，真正同步来源由 `binding_object_type + binding_object_id` 指定

### 4. `im_message`
- 用途：消息主表
- 关键字段：
  - `id`
  - `conversation_id`
  - `seq_no`
  - `sender_type`
  - `sender_id`
  - `message_type`
  - `content_json`
  - `quoted_message_id`
  - `status`
  - `sent_at`
  - `edited_at`
- 说明：
  - 附件通过 `sys_attachment_ref` 关联，建议 `owner_type='im_message'`
  - `content_json` 承载文本、卡片、系统消息等结构化内容
  - 写入消息时需要和 `im_conversation.last_message_seq` 更新保持同一事务口径

## 十六、当前刻意不做的过度抽象

为了保证第一版可落地，当前草图刻意不采用以下设计：
- 不做平台级多租户表
- 不做所有业务统一一张超大表
- 不做员工与管理员共用账号表
- 不做过早的微服务拆库
- 不把向量库当作业务真相源
- 不把权限全部设计成难以理解的动态表达式系统
