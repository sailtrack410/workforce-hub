# 项目确认记录

## 一、产品与部署定位

### 1. 产品定位
- 平台定位为企业内部协同办公平台
- 不是开放式多租户 SaaS 平台
- 核心目标是团队办公、组织协同、审批流程、考勤假期、群组沟通、Agent 辅助

### 2. 交付模式
- 采用单客户独立部署模式
- 每个客户单独部署一套系统
- 系统部署在客户自己的服务器上

### 3. 租户策略
- 第一版不引入平台级多租户
- 系统按单实例单企业设计
- 如果客户内部有总公司、分公司、子公司，统一按组织体系建模
- 分公司/子公司不抽象为租户

## 二、系统形态

### 1. 架构形态
- 第一版采用模块化单体架构
- 不采用微服务
- 按业务域分模块，先逻辑解耦，后物理解耦

### 2. 容器化交付
- 交付目标采用 Docker Compose 容器化部署
- 当前阶段仍按普通项目方式开发
- 容器化属于交付层能力，不改变当前业务代码写法

## 三、存储与基础设施

### 1. 数据存储方案
- 主业务库：MySQL
- 向量检索库：PostgreSQL + pgvector
- 缓存：Redis

### 2. 当前结论
- 主业务数据继续使用 MySQL
- 向量化、知识切片、相似度检索等使用 PostgreSQL + pgvector
- Redis 用于缓存、会话、幂等、限流、短期状态

## 四、后端技术栈

### 1. 主体技术栈
- Java 17（统一作为本地开发、CI、Docker 交付基线）
- Maven
- Spring Boot 3.x
- Spring Security
- MyBatis-Plus + MyBatis XML
- Flowable
- Spring AI
- Spring WebSocket
- Spring Scheduling
- OpenAPI / Swagger

### 2. 后端选型原则
- 业务系统优先，AI 深度嵌入，但不反客为主
- 单表 CRUD 以 MyBatis-Plus 提效
- 复杂查询、报表、权限 SQL 采用 MyBatis XML
- 审批流采用成熟流程引擎，不自行从零实现
- Agent 运行采用统一框架，不并行引入多套 AI 框架

## 五、前端总体策略

### 1. 前端产品划分
- 管理后台与员工/领导端分开设计
- 管理后台是标准 B 端后台风格
- 员工/领导端是企业协同工具风格
- 小程序后置，第一阶段不进入主开发范围

### 2. 前端技术方向
- 管理后台与员工 Web 都基于 Vue 技术栈
- 采用两个独立 Web 应用，而不是一个应用里硬分两套页面体系
- 建议采用同仓库多应用管理方式

### 3. 前端工程拆分原则
- 一个代码仓统一管理
- 两个独立 Web 应用
- 共享 SDK、类型、常量、鉴权工具
- 不共享布局、导航、页面组件、视觉体系

## 六、管理后台结论

### 1. 后台定位
- 管理后台承担治理、配置、规则、审计、Agent 管理等职责
- 页面风格按标准后台治理型产品设计

### 2. 后台设计方向
- 适合标准 B 端页面体系
- 强调树、表格、表单、抽屉、弹窗、治理效率

## 七、员工/领导端结论

### 1. 员工端产品定位
- 员工/领导端不是后台缩小版
- 产品形态参考钉钉、飞书、企业微信等企业协同工具
- 定位为团队办公平台

### 2. 当前阶段策略
- 第一版先做 Web
- 小程序后续再做

### 3. 员工端体验原则
- UI 不能简陋
- 要有完整视觉层次和产品感
- 使用适度动画增强体验
- 动画服务于层级、状态反馈和任务完成感，不追求炫技

## 八、employee-web 主结构

### 1. 默认入口
- 默认入口为消息
- 消息是主工作入口，不是附属模块

### 2. 页面主骨架
- 最左侧：一级功能栏
- 第二列：当前功能列表区
- 第三列：主内容区
- 最右侧：上下文详情栏

### 3. 详情栏策略
- 右侧详情栏默认收起
- 只在需要时展开
- 用于展示会话详情、群信息、成员信息、文档属性、业务上下文等辅助内容

### 4. 一级功能栏
- 消息
- 待办
- 文档
- 工作台
- 我的

### 5. 内容切换方式
- 最左侧一级功能栏负责切换业务域
- 右侧内容根据左侧功能项变化
- 默认进入消息视图

## 九、消息页结构结论

### 1. 消息页定位
- 消息页是员工端的默认工作界面
- 主入口不是传统门户式工作台，而是协同沟通界面

### 2. 消息页结构
- 左侧消息列表
- 中间会话内容区
- 右侧上下文详情栏默认收起

### 3. 消息页设计原则
- 消息承载沟通
- 待办承载任务
- 工作台承载功能导航
- 产品整体更接近办公工具，而不是后台式门户首页

## 十、登录与认证体系结论

### 1. 身份主体划分
- 业务用户：员工、领导，共用一套业务账号体系
- 管理员：独立后台账号体系，不进入组织树
- Agent：系统身份，不作为人类账号登录

### 2. 业务用户账号策略
- 员工和领导使用同一套业务账号体系
- 领导不是独立账号类型，而是员工能力上的增强身份
- 是否具备领导能力，由组织关系与权限规则决定

### 3. 管理员账号策略
- 管理员独立于业务用户体系
- 后台账号单独管理、单独授权、单独审计
- 即使现实中同一人兼具员工和管理员身份，也按两种身份处理

### 4. 登录入口策略
- `employee-web` 使用员工/领导登录入口
- `admin-web` 使用管理后台独立登录入口
- 员工端与后台端会话隔离、权限隔离

### 5. 第一版认证方式
- 第一版采用账号密码登录
- 业务用户支持绑定邮箱
- 绑定邮箱后可接收邮箱验证码
- 邮箱验证码用于身份校验、敏感操作验证、密码找回等场景

### 6. 会话与认证实现方向
- 认证与授权框架采用 Spring Security
- 会话建议采用服务端会话模式
- Redis 用于登录会话、验证码、短期认证状态存储
- 当前不优先采用纯 JWT 作为第一版主会话方案

### 7. Agent 认证原则
- Agent 不走人类登录流程
- Agent 以系统身份运行
- Agent 的访问能力依赖后台授权与工具权限控制
- Agent 的所有动作必须可审计、可追溯

## 十一、权限矩阵骨架结论

### 1. 权限主体划分
- 权限主体分为：员工、领导、管理员、Agent
- 员工、领导、管理员、Agent 不是简单角色叠加关系，而是四类不同主体

### 2. 权限层次划分
- 模块准入权限
- 功能操作权限
- 数据范围权限
- 工具 / 系统权限

### 3. 员工权限原则
- 员工默认具备消息、待办、文档、工作台、我的等业务入口权限
- 员工可发起业务申请
- 员工默认只看自己相关业务数据
- 员工只能访问自己参与的会话、群组与被授权文档

### 4. 领导权限原则
- 领导不是后台用户，而是员工增强身份
- 领导权限 = 员工基础能力 + 团队管理能力
- 领导具备审批、团队查看、团队业务处理能力
- 领导的数据范围覆盖自己及其管理范围

### 5. 管理员权限原则
- 管理员是治理主体，不是领导权限放大版
- 管理员只进入后台治理体系
- 管理员负责组织、流程、规则、群组治理、Agent、知识库、连接器等后台能力
- 管理员不默认进入业务协同会话

### 6. Agent 权限原则
- Agent 不走人类登录，不属于人类账号体系
- Agent 通过会话、流程、任务、事件等业务上下文参与系统运行
- Agent 的访问与执行能力依赖后台授权
- Agent 的所有动作必须可审计、可追溯

### 7. Agent 权限总原则
- Agent 最终权限 = Agent 自身授权 ∩ 当前用户可见范围 ∩ 当前业务场景范围

### 8. 会话与群组权限原则
- 私聊准入规则：直属上级、直属下级、同群成员
- 群组支持组织群、业务群、自定义群
- 群组内存在群主、群管理员、普通成员等不同管理层级
- 管理员负责群组治理策略，但不默认查看员工业务会话内容

### 9. Agent 工具权限原则
- Agent 第一版默认只读优先
- Agent 可调用少量低风险写入型工具
- 高风险动作必须人工兜底，不默认允许自动执行

## 十二、当前已经明确不做的方向

### 1. 架构层
- 第一版不做微服务
- 第一版不做平台级多租户

### 2. 前端层
- 第一版不优先做小程序
- 员工端不做后台缩小版

### 3. Agent 层
- 不并行引入多套 Agent 框架
- 不把 Agent 简化为只有 Prompt 的单一能力
