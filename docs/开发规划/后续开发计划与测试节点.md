## 三、固定测试基线

### 1. 基础回归命令

每个后端 commit 提交前至少执行：

```bash
cd server && mvn -DskipTests compile
cd server && env TEST_DB_NAME=<unique_name> mvn -Dtest=ModuleAuthApiIntegrationTest,ModuleOrgApiIntegrationTest,ModuleOrgWriteApiIntegrationTest,ModuleFileApiIntegrationTest,ModuleFileAdminApiIntegrationTest,ModuleFileCleanupIntegrationTest,ModuleWorkflowFlowableIntegrationTest,ModuleWorkflowAdminApiIntegrationTest,ModuleWorkflowAgentPreReviewIntegrationTest,ModuleLeaveApiIntegrationTest,ModuleLeaveWorkflowIntegrationTest,ModuleAttendanceApiIntegrationTest test
```

IM/Agent 相关提交必须追加：

```bash
cd server && env TEST_DB_NAME=<unique_name> mvn -Dtest=ModuleImApiIntegrationTest,ModuleImGroupIntegrationTest,ModuleAgentApiIntegrationTest,ModuleAgentTaskTimeoutIntegrationTest,ModuleAgentTaskTimeoutRepositoryBoundaryTest test
cd server && env TEST_DB_NAME=<unique_name> mvn -Dtest=ModuleImOutboxIntegrationTest test
```

前端 employee-web 相关提交必须追加：

```bash
cd employee-web && npm test
cd employee-web && npm run build
```

### 2. 测试命名规则

- `TEST_DB_NAME` 必须每次使用唯一库名，避免集成测试互相污染。
- 不允许多个测试套件共享同一个 Redis session namespace。
- Flowable 专用测试必须清理业务表和 `ACT_RU_*` / `ACT_HI_*` 运行时历史表，保留部署定义表。
- Flyway 迁移必须覆盖空库顺序执行；涉及旧库兼容时还要写清楚旧库和半成品库语义。

### 3. 审查完成标准

每个提交完成不只等于“代码写完 + 测试通过”，还必须能按 `docs/审查/审查规范.md` 写清楚：

- 位置
- 触发条件
- 失败路径
- 影响范围
- 修复方向

写不出这五项，说明提交边界或代码理解还不够清楚。

## 五、节点 1：接入真实大模型推理

### 开发内容

- 将 `AgentService.createConversationReplyTask` 当前 mock 规则回复替换为真实模型调用。
- 优先实现 OpenAI 兼容协议客户端，配置可切换通义、豆包、DeepSeek、OpenAI 等兼容端点。
- API key、base URL、model、timeout、max tokens 从配置注入，禁止代码内 fallback 到假回复。
- 第一版只做基础对话，不做工具调用和 RAG。
- Agent 会话任务从同步 mock 改为异步执行：
  - 创建任务后先落 `RUNNING`。
  - 模型调用成功后回写 `SUCCEEDED` 并通知 IM。
  - 模型调用失败后回写 `FAILED`，复用第 72 审已经建立的失败可见性链路。
- 记录模型请求失败类型、响应耗时、provider、model 和必要审计字段，避免失败只留日志。

### 小测试

必须覆盖：

- 配置缺失时服务启动或调用失败语义明确，不能静默走 mock。
- 模型成功返回后 Agent 任务变为 `SUCCEEDED`，IM 生成 Agent 回复消息。
- 模型超时或 5xx 后 Agent 任务变为 `FAILED`，IM 生成失败提示消息。
- 重复回调或重复执行不会生成重复 Agent 回复。
- API key 不出现在响应、审计详情和普通日志里。

建议测试类：

- `ModuleAgentApiIntegrationTest`
- `ModuleImApiIntegrationTest`
- 新增 `ModuleAgentModelClientIntegrationTest`
- 新增 `ModuleImAgentRealModelIntegrationTest`

### 大测试

必须覆盖：

- `auth + org + im + agent` 全链路回归通过。
- 真实模型关闭或不可达时，IM 主会话能力不被拖垮。
- 模型失败必须能被后台 Agent 任务查询、失败聚合和审计轨迹看到。

## 六、节点 2：WebSocket 消息可靠投递

### 开发内容

- 新增 `im_event_outbox` 表，所有 IM 推送事件先入库：
  - `IM_MESSAGE_CREATED`
  - `IM_AGENT_MESSAGE_CREATED`
  - `IM_AGENT_REPLY_FAILED`
  - 后续群成员变更、编辑撤回、已读位点也应复用同一 outbox。
- 事务内只写业务表和 outbox，不直接把“推送成功”作为业务成功条件。
- 新增 dispatcher 异步扫描 outbox，按事件类型推送 WebSocket。
- 推送失败进入可重试状态，记录失败原因、重试次数、下一次重试时间。
- 超过最大重试次数后进入 `DEAD` 或 `FAILED`，后台可观测。
- WebSocket 补偿也必须走 outbox，不允许写临时日志后人工猜测。

### 小测试

必须覆盖：

- 消息发送成功后 outbox 同事务落库。
- dispatcher 成功推送后 outbox 标记 `SENT`。
- 推送异常后 outbox 保持可重试，并记录失败原因。
- dispatcher 重复执行不会重复改变业务消息。
- Agent 回复失败事件也进入 outbox 并最终推送。

建议测试类：

- `ModuleImApiIntegrationTest`
- `ModuleImGroupIntegrationTest`
- `ModuleImOutboxIntegrationTest`
- 新增 `ModuleImWebSocketDispatchIntegrationTest`

### 大测试

必须覆盖：

- 数据库提交成功但 WebSocket 不可用时，消息不会丢失。
- 服务重启后未发送 outbox 可继续派发。
- outbox 迁移在空库和已有 V13 库上都能顺序执行。

## 七、节点 3：IM x Agent SPI 命令对象化

### 开发内容

当前 `ImAgentTriggerService.triggerConversationReply` 和 `ImAgentResultCallback.onAgentReply` 参数过散。下一阶段改为显式命令/结果对象：

- `ImAgentTriggerCommand`
  - `conversationId`
  - `sourceMessageId`
  - `agentId`
  - `triggerUserId`
  - `clientRequestId`
  - `idempotencyKey`
  - `metadata`
- `ImAgentReplyResult`
  - `conversationId`
  - `sourceMessageId`
  - `agentTaskId`
  - `replyMessageId`
  - `status`
  - `failureType`
  - `failureMessage`
  - `idempotencyKey`

目标不是形式重构，而是把真实模型异步执行所需字段显式化，避免异步路径靠隐式约定串联。

### 小测试

必须覆盖：

- source message、agent task、client request、idempotency key 能完整传递。
- 同一 `idempotencyKey` 重复触发只创建或回放同一任务。
- Agent 回写缺失 `sourceMessageId` 或 `agentTaskId` 时拒绝。
- 失败类型能被 IM 失败消息和 Agent 后台查询同时看到。

建议测试类：

- `ModuleImApiIntegrationTest`
- `ModuleAgentApiIntegrationTest`
- 新增 `ModuleImAgentSpiIntegrationTest`

### 大测试

必须覆盖：

- SPI 层仍保持跨模块边界，IM 不直接 import Agent 内部仓储或内部 Row。
- Agent 不直接 import IM 内部服务实现，只依赖 SPI。
- workflow 的 Agent 回写 SPI 不被 IM 改造破坏。

## 八、节点 4：服务拆分与仓储边界治理

### 开发内容

触发条件已经满足：`ImService`、`AgentService`、`WorkflowService`、`AttendanceService`、`AgentRepository`、`WorkflowRepository`、`AttendanceRepository` 均已接近或超过继续扩展前的拆分阈值。outbox 和真实模型接入前，至少先拆 IM 和 Agent：

- `ImConversationService`：会话创建、列表、详情、偏好。
- `ImMessageService`：文本/附件消息、分页、编辑撤回、已读。
- `ImGroupService`：已阶段完成，承载群聊创建、群成员、群治理和群资料；群治理 SQL 已迁入 `ImGroupRepository`。
- `ImAgentConversationService`：Agent 触发、Agent 回写、失败消息。
- `AgentConversationService` 或 `AgentTaskExecutionService`：会话 Agent 执行、模型调用、任务状态机。

拆分原则：

- 不改变对外 API 行为。
- 不顺手加新业务能力。
- 每次拆分只移动一类职责，并保留原测试绿灯。
- Repository 同步按聚合拆，不再让一个仓储承载所有 SQL。

### 小测试

必须覆盖：

- 拆分前后 IM 所有现有接口行为不变。
- Agent 任务创建、超时扫描、IM 回写行为不变。
- 权限、幂等、失败可见性测试不减少。

建议测试类：

- `ModuleImApiIntegrationTest`
- `ModuleImGroupIntegrationTest`
- `ModuleAgentApiIntegrationTest`
- `ModuleAgentTaskTimeoutIntegrationTest`
- `ModuleAgentTaskTimeoutRepositoryBoundaryTest`

### 大测试

必须覆盖：

- 基础回归命令通过。
- IM/Agent 目标回归通过。
- `git diff --stat` 能体现职责移动，而不是混入功能新增。

## 十、再下一阶段：知识库、RAG 与连接器

只有在真实模型、outbox、SPI 对象和服务拆分完成后，才进入知识库和连接器：

- `module-doc`：文档空间、文档版本、文档 ACL。

- RAG：Agent 绑定知识空间、检索授权、引用来源返回。
- connector：外部系统凭证托管、权限边界、调用审计。

该阶段不允许绕过文件中心和 ACL 直接把文档喂给 Agent。所有知识检索必须能回答“谁能看、为什么能看、返回了哪段来源”。

## 十一、提交与审查规则

- 一个 commit 只做一件事，功能、修 bug、拆服务、测试基线和文档刷新分开提交。
- Commit message 用中文，直接描述新增或修复的业务能力。
- 文档与代码同 commit：接口改动同步 API 文档，模块改动同步开发日志，审查产出同步 `docs/审查/README.md`。
- 跨模块调用必须经 SPI，禁止直接 import 另一个模块的内部类、内部 Row 或内部 Repository。
- Flyway、权限边界、状态机三类改动必须在审查里单独列清楚。
- P0/P1 当下修，P2 进入开发规划并明确节点，不写“后续再说”。
- 工作区超过 5 天未提交，或 dirty 内容跨 2 个以上模块，必须优先收口。
- 新模块准入前必须具备 SPI 骨架、Flyway 迁移、IntegrationTest 红灯用例、开发日志、API 与测试文档骨架。
