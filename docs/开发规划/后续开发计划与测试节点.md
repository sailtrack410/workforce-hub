# 后续开发计划与测试节点

## 一、文档目的

本文档基于当前已完成代码与文档状态，整理 `workforce-hub` 后续开发顺序，并为每个开发节点设置两个测试关口：

- 小测试：验证当前模块功能是否完整，重点看模块内部接口、状态、数据、异常和审计。
- 大测试：验证当前模块与系统已完成底座是否兼容，重点看认证、组织、文件、权限、事件、数据复位和全量回归是否被破坏。

本文档不是替代 `docs/开发规划/开发流程总览.md`，而是把后续执行步骤进一步落成可检查节点。

- 工具调用写入 `agt_tool_call_log`。
- 高风险任务必须等待人工确认。
- 未授权工具不能被调用。

建议测试类：

- `ModuleAgentApiIntegrationTest`
- `ModuleAgentTaskIntegrationTest`
- `ModuleAgentToolIntegrationTest`

### 大测试：Agent 与业务系统兼容性

必须覆盖：

- 会话 Agent 结果能回写 `module-im`。
- 流程预审结果能回写 `module-workflow`。

- Agent 访问知识库只能访问绑定空间。

## 五、固定测试分层规则

后续每个模块都统一采用下面规则，避免测试口径漂移。

### 1. 小测试规则

小测试只回答一个问题：

当前模块自己的功能是否完成？

要求：

- 每个模块至少一个 `ModuleXxxApiIntegrationTest`。
- 写侧模块必须覆盖成功路径、失败路径、权限路径、状态路径。
- 有状态机的模块必须断状态流转。
- 有审计的模块必须断审计落点。
- 有事件的模块必须断事件发布。
- 有幂等要求的模块必须断重复请求不会重复写数据。

### 2. 大测试规则

大测试回答另一个问题：

当前模块接入系统后，是否破坏或兼容已有模块？

要求：

- 每完成一个节点，至少跑一次当前模块加所有已完成核心模块的组合测试。
- 所有新增表必须加入测试库复位逻辑。
- 所有新增接口必须验证未登录、错端身份、无权限场景。
- 所有跨模块调用必须至少有一个集成测试覆盖。
- 所有 Flyway 迁移必须能从空库顺序执行。

### 3. 当前固定回归基线

当前已经形成的基础回归命令：

```bash
cd server && mvn -DskipTests compile
cd server && mvn -Dtest=ModuleAuthApiIntegrationTest,ModuleOrgApiIntegrationTest,ModuleOrgWriteApiIntegrationTest,ModuleFileApiIntegrationTest,ModuleFileAdminApiIntegrationTest,ModuleFileCleanupIntegrationTest,ModuleWorkflowFlowableIntegrationTest,ModuleWorkflowAdminApiIntegrationTest,ModuleWorkflowAgentPreReviewIntegrationTest,ModuleLeaveApiIntegrationTest,ModuleLeaveWorkflowIntegrationTest,ModuleAttendanceApiIntegrationTest test
```

后续每完成一个新模块，就把新模块测试类加入这条大测试命令。

## 六、优先级结论

下一步优先级建议如下：

1. 先完成 `module-file` 第三批，补后台文件治理和清理任务。
2. `module-workflow` 已跑通请假申请到领导审批的第一批闭环，并补齐审批附件下载授权、模板治理、Agent 预审入口和 `module-leave` 余额扣减联动。
3. `module-attendance` 已完成打卡、异常、排班、请假通过联动、实时打卡可信边界和请假分钟级覆盖，下一步优先补补卡申请审批闭环、排班唯一模型修复和统一日结果重算锁。
4. 再做 `module-im`，因为消息附件和组织准入已经有底座可复用。
5. 最后把 `module-agent`、`module-doc`、`module-kb` 接入真实业务场景，而不是空跑 Agent。

这样推进的好处是，每一个节点都能交付一个可运行、可测试、能接入下一节点的系统能力。
