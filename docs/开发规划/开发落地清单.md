# 开发落地清单

> 说明：
> - 本文档负责“当前阶段具体要补什么”
> - `docs/开发规划/开发流程总览.md` 负责“整个项目按什么阶段推进”

## 一、当前阶段要先确定什么

基于《平台总导图》，现在不建议继续扩导图，而是开始把导图落成可开发文档。

当前优先级最高、必须先确定的内容有 8 类：

### 1. V1 业务边界
- 第一版必须上线哪些模块
- 第一版明确不做哪些模块
- 各模块之间的先后依赖关系

当前建议的 V1 主线：
- 组织与用户
- 登录与权限
- 请假 / 补卡 / 审批流程
- 考勤与假期余额
- 基础消息与群组
- 会话问答 Agent
- 流程预审 Agent

### 2. 核心数据模型
- 用户、部门、汇报关系
- 角色与权限范围
- 考勤组、班次、工作日历
- 假期账户与余额变动
- 流程模板、流程实例、审批任务
- 会话、群组、消息
- Agent、工具、知识库、连接器

这一部分要解决的是：
- 有哪些核心表
- 谁引用谁
- 哪些字段是快照
- 哪些字段是配置
- 哪些字段是运行态数据

### 3. 状态机
- 员工状态
- 流程实例状态
- 审批任务状态
- 群组状态
- Agent 任务状态
- 知识入库任务状态

这一部分要解决的是：
- 一个对象有哪些状态
- 什么动作会触发状态变化
- 哪些状态可撤回
- 哪些状态不可逆

### 4. 权限矩阵
- 员工能看什么、做什么
- 领导能看什么、做什么
- 管理员能看什么、做什么
- Agent 能调用什么、不能调用什么

这一部分要解决的是：
- 页面权限
- 数据权限
- 操作权限
- 工具权限
- 外部连接器权限

### 5. 流程运行规则
- 加签
- 转审
- 退回
- 委托代理
- 催办
- 超时升级
- 模板版本与生效时间
- Agent 预审的通过 / 驳回 / 转人工规则

这一部分要解决的是：
- 流程到底怎么跑
- 哪些动作是人工
- 哪些动作可自动执行
- 在途流程如何与模板版本隔离

### 6. Agent 运行模型
- Agent 的组成结构
- Agent 的触发方式
- Agent 的工具调用机制
- Agent 的失败重试与人工兜底
- Agent 的审计与留痕

这一部分要解决的是：
- Agent 不是“一个 Prompt”，而是一套运行单元
- Agent 是如何被创建、测试、发布、停用的
- Agent 什么时候可以自动执行，什么时候只能建议

### 7. 技术栈与模块拆分
- 后端技术栈
- 前端技术栈
- 消息 / 推送 / 搜索 / 附件 / 缓存 / 任务调度方案
- AI / RAG / 工具调用方案
- 单体还是模块化单体，还是微服务

这一部分要解决的是：
- 开发语言和框架
- 模块边界
- 基础中间件
- 后续扩展成本

### 8. 非功能与基础设施要求
- 登录认证
- 单点登录
- 文件附件
- 推送通道
- 监控告警
- 审计日志
- 凭证托管
- 数据备份与恢复

这一部分要解决的是：
- 能不能上线
- 出问题能不能追溯
- 自动化能力会不会失控

## 二、现在最适合先出的文件

建议先按下面顺序产出文档，而不是同时开很多文件。

### 1. 核心表结构草图
建议文件名：
- `docs/架构与设计/核心表结构草图.md`

内容建议：
- 分模块列出核心表
- 每张表写用途
- 每张表列核心字段
- 标注主键、外键、唯一约束
- 标注哪些字段是快照字段

### 2. 状态机设计
建议文件名：
- `docs/架构与设计/状态机设计.md`

内容建议：
- 员工状态流转
- 流程实例状态流转
- 审批任务状态流转
- Agent 任务状态流转
- 知识入库任务状态流转

### 3. 权限矩阵
建议文件名：
- `docs/架构与设计/权限矩阵.md`

内容建议：
- 角色 x 模块 x 动作
- 数据可见范围
- 群组与会话权限
- Agent 工具权限
- 管理后台治理权限

### 4. 技术栈与架构方案
建议文件名：
- `docs/架构与设计/技术栈与架构方案.md`

内容建议：
- 前后端框架
- 数据库与缓存
- 消息与推送
- 搜索与附件
- Agent / RAG / 工具调用
- 部署方式

### 5. 接口与事件清单
建议文件名：
- `docs/架构与设计/接口与事件清单.md`

内容建议：
- 组织与用户接口
- 流程发起与审批接口
- 会话与群组接口
- Agent 调用与任务接口
- 知识库入库与检索接口
- 系统事件与订阅

## 三、推荐的落实顺序

推荐顺序如下：

1. 先定 V1 业务边界
2. 再出核心表结构草图
3. 再补状态机设计
4. 再补权限矩阵
5. 再定技术栈与模块划分
6. 最后出接口与事件清单

原因是：
- 表结构会反推你哪些对象还没想清楚
- 状态机会暴露流程和 Agent 的真实复杂度
- 权限矩阵会暴露角色边界是否自洽
- 技术栈应该服务于业务模型，而不是先拍脑袋定

## 四、当前最应该优先推进的两个文件

如果只选两个文件先做，建议是：

### 1. `docs/架构与设计/核心表结构草图.md`
这是所有开发工作的真正起点。

### 2. `docs/架构与设计/技术栈与架构方案.md`
这是决定后端工程骨架和前后端协作方式的基础。

## 五、建议的当前结论

基于目前仓库状态，当前最合理的推进方式是：

- 用《平台总导图》作为总纲，不再继续扩导图
- 先产出 `docs/架构与设计/核心表结构草图.md`
- 紧接着产出 `docs/架构与设计/技术栈与架构方案.md`
- 然后再补 `docs/架构与设计/状态机设计.md` 与 `docs/架构与设计/权限矩阵.md`

如果按这个顺序推进，后面就可以自然进入：
- 后端工程初始化
- 数据库建模
- 模块划分
- 前端菜单与路由设计
- Agent 运行框架落地
