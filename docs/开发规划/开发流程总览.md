# 开发流程总览

## 一、目的

这份文档用于把 `workforce-hub` 第一版的开发工作拆成可执行的阶段流程。

目标不是泛泛而谈“先做后端、再做前端”，而是明确：

- 整个项目分成哪几个主流程
- 每个主流程下面有哪些子流程
- 每个流程的前置依赖是什么
- 每个流程的阶段产出是什么
- 当前做到哪一步，下一步该接什么

---

## 二、整体结论

第一版建议拆成 `8` 个主流程，按顺序推进：

1. 开发基线与工程底座
2. 认证与组织主链路
3. 审批、假期、考勤业务主链路
4. 消息、会话、群组协同主链路
5. Agent 运行主链路
6. 文档、知识库、RAG 主链路
7. 后台治理与运维支撑主链路
8. 联调、测试、交付主链路

其中：

- `1` 已经基本完成
- `2` 已完成认证、组织查询、组织写侧、组织领域事件等关键底座
- `3` 到 `8` 还未正式进入完整业务闭环阶段

当前正在补一条跨流程共享底座：

`module-file 文件中心第一版`

原因很简单：

- 消息附件、群文件、审批附件、文档、知识库和 Agent 临时产物都会依赖统一文件底座
- 先把上传、去重、配额、下载票据和回收站做稳，后续协同、知识库和 Agent 不需要重复造文件能力

## 三、主流程拆解

### 1.2 子流程

#### 1.2.1 文档骨架收口

- 平台总导图
- 项目确认记录
- 技术栈与架构方案
- 核心表结构草图
- 状态机设计
- 权限矩阵
- 接口与事件清单

#### 1.2.2 后端工程骨架初始化

- Spring Boot 工程初始化
- 公共响应、异常、枚举
- MyBatis-Plus、Flyway、Redis、Security 基础接入
- Flowable 精简依赖接入
- SPI 接口骨架落位

#### 1.2.3 本机环境基线收口

- JDK 17
- Maven 可编译
- MySQL、Redis 可用
- `.env.example`

### 1.3 阶段产出

- 可编译的 `server/` 工程
- 可持续扩展的骨架文档
- 本机最小运行环境

### 1.4 当前状态

`基本完成`

## 2. 认证与组织主链路

### 2.1 目标

建立“谁能登录、是谁、属于哪个组织、上下级是谁、能看哪些数据”的统一底座。

### 2.2 子流程

#### 2.2.1 认证流程

- 员工账号密码登录
- 后台管理员登录
- Session 写入与销毁
- 当前用户信息查询
- 邮箱验证码
- 邮箱绑定
- 找回密码
- 登录失败频控

#### 2.2.2 组织模型流程

- 部门树管理
- 岗位管理
- 员工档案管理
- 直属上级绑定
- 部门负责人绑定
- 员工入转调离事件记录

#### 2.2.3 账号与员工映射流程

- `auth_user_account` 与 `org_user` 绑定
- 员工状态对登录准入的影响
- 后台账号与业务员工账号隔离

#### 2.2.4 数据权限底座流程

- 员工仅看本人数据
- 直属领导可看下属数据
- 管理员按角色治理数据
- 为后续审批、消息、群组、Agent ACL 提供统一身份上下文

### 2.3 前置依赖

- 第 1 流程完成

### 2.4 阶段产出

- 员工端登录闭环
- 后台端登录闭环
- 组织树与员工档案 API
- 上下级关系可查询
- 基础数据权限可落地

### 2.5 当前状态

`进行中`

### 2.6 当前状态

当前已经完成：

1. `module-auth` 员工端、后台端认证闭环
2. 邮箱验证码、邮箱绑定、密码重置和真实 SMTP 冒烟入口
3. `module-org` 部门、岗位、员工查询接口
4. `module-org` 后台写侧治理接口
5. 员工生命周期与账号启停联动
6. 组织领域事件发布与事件断言

下一步不再继续扩大 `module-org`，而是先补 `module-file` 文件中心底座。

## 四、推荐开发顺序

按你这个项目的实际情况，推荐顺序不是“模块平均推进”，而是“先打主链，再补横向能力”：

1. 认证与组织
2. 审批、假期、考勤
3. 消息、会话、群组
4. Agent 运行框架
5. 文档、知识库、RAG
6. 后台治理
7. 联调、测试、交付

这样做的原因是：

- 审批、消息、Agent 都依赖组织与身份
- Agent 的价值要建立在真实业务流程和真实知识数据之上
- 后台治理适合在对象已经基本成型后集中补齐

## 六、现在最应该做什么

如果按“既符合依赖顺序、又最能形成下一阶段基础”的标准，接下来最推荐做的是：

### 方案 A：先做 `module-org`

子流程顺序建议：

1. 部门表、岗位表、员工表、部门负责人表的 Mapper / Service / Controller
2. 部门树查询
3. 员工列表与详情
4. 直属上级 / 下级查询
5. 新增员工、编辑员工、上下级绑定

这条路的好处是：

- 能立刻支撑消息私聊规则
- 能立刻支撑审批链路找领导
- 能立刻支撑 Agent ACL 与组织范围判断

### 方案 B：先把 `module-auth` 做到真实可用

子流程顺序建议：

1. 真实 SMTP 验证码联调
2. 找回密码闭环验证
3. 绑定邮箱闭环验证
4. 员工状态与登录准入联合校验

这条路的好处是：

- 认证底座更稳
- 后面前端一接登录就不容易返工

### 当前更推荐

`先做方案 A，再补方案 B 的真实发信联调`

原因是：

- `module-auth` 现在已经“能继续开发”
- `module-org` 还没落下来，而它会卡住更多后续模块

## 九、结论

现在这个项目已经不是“还在想能不能做”的阶段了，而是进入了“按阶段推进实现”的阶段。

对当前来说，最重要的不是再扩想法，而是按顺序推进：

1. 先把 `开发流程总览` 定下来
2. 再按它进入 `module-org`
3. 然后推进审批、消息、Agent 三条真正体现产品价值的主链

如果按这个节奏走，整个项目会非常稳，不容易失控。
