# 插件签名清单信任边界设计

## 目标

安装和启动恢复只能信任已签名 JAR 内的 `plugin.json` 来决定插件类型、发布方、前端产物摘要和必需依赖，禁止安装请求或未核对的 PF4J 描述符改写这些字段。

## v0.1 清单契约

```json
{
  "id": "hello-plugin",
  "version": "0.1.0",
  "sdkVersion": "0.1.0",
  "minHostVersion": "0.1.0",
  "maxHostVersion": "0.2.0",
  "javaVersion": "17",
  "type": "UI",
  "provider": "Workforce Hub",
  "frontendSha384": "sha384-c527zMMh7jwa0gTNl9fI1Mg5xEqGXyEFnTFCcjr7fokaoyPHzkIY7kC9f13c4zUQ",
  "dependencies": []
}
```

| 字段 | 规则 |
|------|------|
| `type` | 必填，只允许 `UI` 或 `FUNCTIONAL` |
| `provider` | 必填，必须是非空字符串 |
| `frontendSha384` | `UI` 必填，格式必须是单个 `sha384-` 加 64 位 Base64；`FUNCTIONAL` 禁止声明 |
| `dependencies` | 可选数组，最多 128 个必需依赖；只允许 `pluginId/minVersion/maxVersion`，版本为严格 SemVer 闭区间 |

`frontendEntry` 不进入签名清单。宿主始终根据已签名的插件 ID 生成 `/plugins/{pluginId}/index.js`，不接受上传方提供任意脚本路径。

## 数据流

1. 宿主先把上传 JAR 复制到 `pluginsRoot/.snapshots` 并完成 RSA 验签。
2. `PluginVersionService` 从该快照中唯一的 `plugin.json` 解析身份、版本、`type`、`provider`、`frontendSha384` 和必需依赖。
3. 宿主在 PF4J 加载前后校验描述符的 ID、版本、依赖必需性和规范化范围与签名清单完全一致。
4. `PluginManagerService.install` 只从解析结果写入运行时字段，并在注册记录事务中写入 `sys_plugin_dependency`；前端入口仍按插件 ID 派生。
5. 安装请求中的同名 metadata 字段全部忽略；`signerId` 和分离签名仍由安装请求提供并由宿主校验。
6. 同 ID 替换时，新包 `signerId` 必须与旧 `UNINSTALLED` 记录一致；其他可信签名者也不能接管旧插件 ID 及其保留配置和授权。
7. `restorePlugins()` 重新验签、重新解析清单，要求数据库记录与清单一致，并按可信依赖图拓扑恢复；缺失、冲突、循环或运行时失败只影响相关插件。
8. 员工清单仅返回 `ACTIVE + UI` 且 SRI 合法的插件，前端加载器继续固定使用 `/plugins/{id}/index.js`。

## 兼容性与边界

- 不提供外部 metadata 回退。旧插件 JAR 缺少新字段时安装或恢复失败，必须重新构建并签名。
- `sys_plugin_dependency` 沿用 V52 结构；V60 仅为 `depends_on` 反向查询新增索引，不修改已发布迁移。
- `name` 和 `description` 本次仍是安装展示信息，不参与代码执行授权；后续若作为可信品牌信息展示，再纳入签名清单。
- `provider` 是已签名声明，不等于证书主体；真正的签名者身份仍以宿主可信公钥白名单中的 `signerId` 为准。
- 前端摘要绑定的是独立交付的 IIFE `index.js`。发布顺序必须是：构建 IIFE → 计算 SHA-384 → 写入 `plugin.json` → 打包 JAR → 对完整 JAR 签名。

## 错误处理

- 缺失、空值、错误类型、未知 `type`、非法 SRI、类型与 SRI 组合冲突，以及依赖未知字段、可选、自依赖、重复、非法或倒置版本范围均在 PF4J 加载和 Flyway 迁移前拒绝。
- PF4J 描述符与签名清单不一致时统一拒绝；启用依赖未满足、损坏版本记录和反向 dependent 阻断映射为脱敏 `409`。
- 安装失败继续沿用现有快照与 PF4J 清理语义。
- 恢复时字段不一致统一使用“插件清单与安装记录不一致”，不向员工端暴露内部字段差异。

## 测试要求

- `PluginVersionServiceTest` 覆盖合法依赖、128 项边界、严格 SemVer、未知字段、自依赖、重复、倒置范围和 PF4J 描述符漂移。
- `PluginManagerSignatureSafetyTest` 覆盖外部 metadata 无法覆盖签名字段、依赖恢复拓扑和失败隔离。
- `PluginManagerServiceIntegrationTest` 覆盖真实签名依赖 JAR 的安装、持久化、启用、反向保护、恢复及 PF4J 描述符不一致。
- `PluginRepositoryDependencyIntegrationTest` 覆盖事务写入/回滚、批量水合、反向查询和 V60 索引。
- `plugin-iife-build.test.ts` 构建 hello-plugin IIFE，计算真实 SHA-384，并断言与 `plugin.json` 一致。
- 最终运行依赖专项、后端完整 reactor 测试和 `git diff --check`；本节点没有前端源码改动。
