# 插件化工作台 - 后端架构

## 技术选型

| 组件       | 技术        | 版本   |
|------------|-------------|--------|
| 插件框架   | PF4J        | 3.15.0 |
| 主框架     | Spring Boot | 3.2.5  |
| 数据库     | MySQL 8.x   | -      |

`WorkforcePluginFactory` 仅负责向插件构造器注入 `PluginContext`；v0.1 没有为插件创建独立 Spring 子 Context。

## 插件管理器

当前实现由两个类分工：

- `WorkforcePluginManager`：唯一 PF4J 管理器，配置插件根目录并使用 `WorkforcePluginFactory`。
- `PluginManagerService`：串行执行安装、恢复、启用、停用和卸载，并同步 `sys_plugin` 状态。

生命周期契约：

| 操作 | 当前流程 | 成功状态 |
|------|----------|----------|
| 安装 `install(Path, PluginRow)` | 复制到 `pluginsRoot/.snapshots` → 对快照验签和校验 `plugin.json` → 忽略外部同名字段并构建最终 `PluginRow` → 校验字段长度并拒绝已存在 ID → PF4J 加载并核对 ID/版本 → 可选 Flyway 迁移 → 写入注册表 | `INSTALLED`，保留快照且不自动启动 |
| 启用 `enable(String)` | PF4J 启动 → 写入状态 → 打开 `PluginLifecycleGuard`；写库失败时仅回滚本次新启动的实例，原本已 `STARTED` 的实例不误停 | `ACTIVE` |
| 停用 `disable(String)` | 若仍有已加载 dependent 则在关门和写状态前拒绝；否则关闭入口 → 标记停用中 → 最多等待 30 秒排空 → PF4J 停止 | `STOPPED`；排空或停止失败为 `ERROR` |
| 卸载 `uninstall(String)` | 若仍有已加载 dependent 则在关门和写状态前拒绝；否则关闭入口并排空 → PF4J 停止、卸载 → 清理守卫 | `UNINSTALLED`，保留数据库记录、业务数据和 `sys_plugin_config` |
| 启动恢复 `restorePlugins()` | 在 `ApplicationStartedEvent` 处理 `ACTIVE`、`INSTALLED`、`STOPPED` 记录；全部复验后加载，仅启动 `ACTIVE` | 保持原状态；失败尝试标记 `ERROR`，状态写入失败仅记录日志并继续后续插件 |

`PluginManagerService` 的生命周期方法均为 `synchronized`，只解决单 JVM 内的并发；多实例恢复所有权仍未定义。`WorkforcePlugin` 使用 final `start()` / `stop()` 包装 `onStart()` / `onStop()` 和逆序 `AutoCloseable` 清理队列，启动失败或停止异常也会继续关闭全部已注册资源；失败动作保留并禁止插件重启或 ClassLoader 卸载，后续停止/卸载可重试。工厂在执行构造器前拒绝未继承该基类的主插件。

`WorkforcePluginManager` 对目标插件及全部依赖者先完成停止检查；任一 wrapper 仍在 PF4J `startedPlugins` 或实例仍有待清理工作时，卸载整体 fail closed。运行时 `disable` / `uninstall` 不做级联：目标仍有已加载 dependent 时直接拒绝。Spring `@PreDestroy` 先关闭全部 wrapper（包括 unresolved）的入口，再等待全部插件排空；只有全体排空成功才开始卸载，任一排空失败都会全局拒绝卸载，避免 PF4J 依赖级联绕过在途回调保护。关闭过程不改写数据库中的 `ACTIVE` 状态。

长期资源只允许在 `onStart()` 调用线程中同步创建并立即注册；`onStart()` 返回后的登记会先关闭传入资源再拒绝。线程和线程池关闭必须由插件注册包含停止信号、interrupt/shutdown 与有界等待的清理动作。插件自有线程负责清理自己的 `ThreadLocal` 和 TCCL；宿主线程中的 `ThreadLocal` 必须在同一次业务回调中 `finally remove()`。

插件 JDBC 驱动必须由插件 ClassLoader 中的清理动作注销准确实例，因为 `DriverManager` 不允许宿主 ClassLoader 可靠枚举或注销子 ClassLoader 注册的驱动。当前自动化使用动态编译插件中的最小 `Driver` 注册表/CallerSensitive 探针验证插件侧注销、宿主侧直接注销被拒绝和 `DriverAction`，不代表已覆盖 MySQL/PostgreSQL 驱动、连接池或厂商后台线程。协议无法发现未注册的 native/global 资源；宿主尚无对插件 `onStop()` / cleanup 的强制执行超时。当前自动化另在隔离 JDK 17 子 JVM 中执行进程级 Java heap 增长阈值回归；该证据不能归因到单个插件，不是生产监控，也不覆盖 native/off-heap/RSS。

安装前会校验最终记录中的 `pluginId(64)`、`name(128)`、`description(512)`、`type(32)`、`jarPath(512)`、`jarSha256(64)`、`signerId(128)`、`frontendEntry(512)`、`frontendSha384(96)`、`provider(128)`，并限制 `signature` 不超过 65535 字节。字段超长或当前已存在同 ID 时，在 PF4J 加载和 Flyway 迁移前失败并删除未持久化快照；该存在性检查不区分状态，因此 `UNINSTALLED` 记录也会阻止同 ID 重装。`exists(pluginId)` 不是多实例锁，不能消除跨实例并发安装竞态。

最终记录中 `type`、`provider`、`frontendSha384` 只来自已签名 `PluginVersionDescriptor`；`UI` 的 `frontendEntry` 按签名插件 ID 固定派生为 `/plugins/{pluginId}/index.js`，`FUNCTIONAL` 为空。安装请求中的同名 metadata 一律忽略，不做回退；旧 JAR 缺少新清单字段时必须重新构建并对完整 JAR 签名。

## 签名校验

首版采用 RSA 分离签名，不把自定义签名文件写入被签 JAR：

1. 发布方使用 `SHA256withRSA` 对完整 JAR 原始字节签名，交付 JAR、签名和 `signerId`。
2. 宿主通过 `workforce.plugin.trusted-signers` 配置不少于 2048 位的 X.509 RSA 公钥白名单。
3. `PluginSignatureVerifier` 流式校验签名并同时计算 JAR SHA-256。
4. `PluginManagerService.install` 先把上传源复制到 `pluginsRoot/.snapshots`，验签、版本读取、PF4J、Flyway 和持久化均使用该快照，数据库保存快照路径与宿主计算摘要。
5. `restorePlugins` 必须使用数据库中的签名、签名者和摘要复验，失败时尝试标记 `ERROR`，禁止加载。

配置格式：

```text
WORKFORCE_PLUGIN_TRUSTED_SIGNERS=official=<BASE64_X509_RSA_PUBLIC_KEY>;backup=<BASE64_X509_RSA_PUBLIC_KEY>
```

未配置可信签名者、签名缺失、签名者未知、JAR 被替换或摘要不一致时均 fail closed。
可信公钥白名单在应用启动时读取，不支持运行时热刷新；配置变更必须重启后才会影响新安装和启动恢复。

`provider` 是 JAR 内的已签名发布方声明，不等于证书主体或真实签名者身份；真实签名者仍以命中可信公钥白名单的 `signerId` 为准。

安装成功保留快照供重启恢复；安装失败且 PF4J 已确认清理完成时删除未持久化快照，PF4J 清理失败时保留快照供重启后处置。上传源在复制完成后被替换不会影响本次安装。

该快照使用随机临时文件名，不是内容寻址，也没有超出操作系统文件权限的不可变保护。同一 OS 账号仍可修改快照；恢复阶段在验签后还会按持久化快照路径多次打开 JAR，因此恢复链路仍有同账号篡改和 TOCTOU 边界。

## 版本校验

`PluginVersionService` 只读取签名校验通过的 JAR 根目录中唯一的 `plugin.json`，文件上限 64KB。版本字段必须使用严格的 `major.minor.patch` 格式。

校验规则：

1. 插件 SDK 不得高于宿主 SDK。宿主 SDK 为 `1.x` 及以上时要求主版本相同；宿主 SDK 为 `0.x` 时还要求次版本相同。
2. 宿主版本必须位于 `minHostVersion` 与可选 `maxHostVersion` 的闭区间内。
3. 插件要求的 Java feature version 不得高于当前运行时。
4. `plugin.json.id` 必须匹配 `^[a-z0-9-]{1,64}$`。
5. `type`、`provider` 必填；`type` 只允许 `UI` 或 `FUNCTIONAL`，`UI` 必须声明合法 `frontendSha384`，`FUNCTIONAL` 禁止声明该字段（包括 `null`）。
6. PF4J 解析出的插件 ID、版本必须与 `plugin.json` 一致。
7. 安装时忽略外部 `type`、`provider`、`frontendEntry`、`frontendSha384`，并只使用签名 descriptor 及宿主固定派生入口。
8. 启动恢复时在 PF4J 加载前比较数据库中的 `type`、`provider`、`frontendEntry`、`frontendSha384` 与签名清单派生值；任一漂移均以“插件清单与安装记录不一致”标记 `ERROR` 并禁止加载。

默认配置：

```properties
workforce.plugin.host-version=0.1.0
workforce.plugin.sdk-version=0.1.0
```

安装顺序固定为：签名校验 → 版本清单校验 → 最终安装记录预检与已存在 ID 检查 → PF4J 加载及身份一致性校验 → Flyway 迁移 → 持久化。PF4J 加载后的步骤失败时会尝试 unload；若 `loadPlugin` 在返回 ID 前因依赖解析失败，宿主会按 JAR 路径识别本次新增 wrapper，并在不卸载依赖者、不重新解析全局依赖的条件下清理，避免影响或误报既有 unresolved 插件。若 PF4J 返回清理失败，错误会向上暴露、未持久化快照会保留，进程可能需要重启才能确认完全释放。

UI 插件发布顺序必须是：构建 IIFE → 计算 SHA-384 → 写入 `plugin.json` → 打包 JAR → 对完整 JAR 签名。任意插件的通用构建、签名和原子发布脚本仍未实现。

## Flyway 迁移

`PluginFlywayMigrator.migrate(pluginId, pluginJarPath)` 的当前契约：

1. 校验 JAR 是普通文件；JAR 内没有 `db/migration/` 时直接跳过，迁移不是必需能力。
2. 为插件生成独立 history 表 `flyway_plugin_{safeId}`。长 ID 或包含非法字符的 ID 会附加原始 ID 的 SHA-256 短摘要，避免简单截断碰撞并满足 MySQL 标识符长度限制。
3. 通过 JAR 文件系统读取 `db/migration/`，把脚本复制到宿主创建的临时目录；不使用错误的 `jarPath.resolve("db/migration")`。
4. Flyway 使用 `baselineOnMigrate=true`、`baselineVersion=0`、`validateOnMigrate=true`、`outOfOrder=false` 执行迁移。
5. 无论成功或失败都删除临时迁移目录；清理失败作为安装失败处理。

当前已把最终安装记录字段超长和检查时已存在的插件 ID 前置到迁移前拒绝，但安装顺序仍是“迁移后写入 `sys_plugin`”。数据库瞬时失败或多实例并发安装竞态仍可能使注册表插入失败，已执行的 MySQL 迁移和插件 history 可能保留；完整安装原子性仍需安装占位状态或跨实例协调，不能宣称数据库可自动回滚。

## 插件配置

当前配置链路由以下组件组成：

- `PluginConfigRepository`：列表查询限定 `plugin_id`，单项读取、更新和删除同时限定 `plugin_id` 与 `config_key`；更新、删除使用 `version` 乐观锁，写入前锁定插件状态行。
- `PluginConfigService`：处理键、类型、大小、数量、状态和版本校验，并在创建、更新、删除成功的同一事务内写脱敏审计。
- `PluginConfigCipher`：对 `SECRET` 使用 AES-256-GCM；每次生成随机 12 字节 nonce，128 位 tag，AAD 为 `pluginId + NUL + configKey`。
- `DefaultPluginConfig`：实现 SDK 只读 `PluginConfig`，优先返回当前值，再回退默认值；敏感值只在插件读取时解密。

`WorkforcePluginManager` 为每个 PF4J pluginId 创建独立 `DefaultPluginConfig`，再由 `WorkforcePluginFactory` 随 `DefaultPluginContext` 注入插件构造器。插件只能调用 `context.getConfig().get(key)` 查询自身命名空间，不能提交其他 pluginId，也没有配置写接口或 typed getter。

管理入口为 `GET /api/admin/plugins/{pluginId}/config`、`PUT /api/admin/plugins/{pluginId}/config/{configKey}` 和带 `expectedVersion` 的单项 `DELETE`。全部路径受 `ADMIN_PLUGIN_MANAGE` 保护；写接口继承全站 Cookie/Header CSRF。`PUT` 拒绝 `DISABLING`、`UNINSTALLED`，`DELETE` 仅拒绝 `DISABLING`，因此管理员仍可显式删除已卸载插件的保留配置。卸载流程本身不级联删除配置。

配置类型只支持 `STRING / INT / BOOL / SECRET`；单值或默认值最多 16 KiB，说明最多 256 字符，配置 PUT 请求体在 Nginx 入口和应用反序列化前均最多 256 KiB，单插件最多 128 个配置键命名空间且墓碑仍计入上限。从未存在过的键使用 `expectedVersion=0` 创建，更新和删除提交当前正版本，删除后同键重建提交 DELETE 返回的墓碑版本；并发同版本写入只允许一个成功。删除会清空配置内容并保留内部版本墓碑；原版本 DELETE 可幂等重试并恢复墓碑版本，不重复写审计。重建继续递增版本，旧创建、更新和删除请求都不能命中新记录；墓碑不参与列表和插件读取，但保留命名空间配额以限制表增长。`requiresRestart` 当前只是元数据，不会自动停用、重启插件或持久化待重启状态。

敏感响应只返回 `secret` 和 `hasValue`，不返回明文、密文或默认值。主密钥来自 `WORKFORCE_PLUGIN_CONFIG_ENCRYPTION_KEY_BASE64`，必须是 Base64 编码的 32 字节值；缺少密钥时普通配置仍可用，所有敏感 PUT fail closed，格式错误则启动失败。`value=null` 的元数据更新必须先用当前密钥解密原密文；缺钥、错钥、损坏或历史明文返回 `422`，提交新值可使用当前密钥重新设置。

当前密文没有 key ID、多密钥、自动轮换、重加密或 KMS 集成。数据库和原主密钥必须分开备份并成对恢复；直接替换或丢失主密钥会使既有敏感配置不可解密。

## 调用上下文绑定

`InvocationContext` 没有公开 Builder。其构造器为 `com.workforcehub.plugin.sdk` 包级可见，只有宿主同包的 `InvocationContextBinder` 能创建上下文。

当前绑定入口：

| 方法 | 身份与来源 |
|------|------------|
| `bindFromRequest(request, pluginId)` | 必须存在当前登录用户；根据用户类型绑定 `USER` 或 `ADMIN`，来源为 `HTTP_REQUEST`；缺少请求 ID 时由宿主生成 UUID |
| `forPluginStartup(pluginId)` | `PLUGIN` / `STARTUP` |
| `forScheduledTask(pluginId)` | `PLUGIN` / `SCHEDULED_TASK` |
| `forEventCallback(pluginId, event)` | `PLUGIN` / `EVENT_CALLBACK`；请求 ID 使用事件 ID，`triggeredBy` 仅接受用户 ID 或 `system` |

插件只能读取 getter，不能调用 `InvocationContext.builder()` 或自行构造身份。

## 事件发布与分发

六类插件事件均由真实业务服务在事务内调用 `DomainEventPublisher.publishAfterCommit` 注册，发布器在无活跃事务时 fail closed，事务回滚不发布。Spring listener 只把显式白名单快照转换为 SDK `DomainEvent`，不回查业务表，也不把审批意见、员工姓名/账号状态、打卡 IP/位置/设备等非契约字段传给插件。

`PluginEventDispatcher` 在原业务线程查询订阅并入队，handler 在共享有界线程池中异步执行：worker 数为 2–8 个 daemon 线程，队列容量 256；队列满时记录并丢弃，不保证同插件或同事件类型的顺序。worker 与 timeout 调度线程创建时使用宿主 ClassLoader 作为 TCCL。回调前逐次重查插件 `ACTIVE` 状态、`PluginLifecycleGuard`、`EVENT_SUBSCRIBE`、事件专项能力、handler 存在性和 `idempotent=true`；回调结束后恢复原 TCCL、清除本次残留中断，再释放生命周期计数。权限撤销只阻止尚未越过检查的回调，已在途回调允许完成。

事件回调执行 `ActionDescriptor.defaultTimeout`：到期时由调度线程中断当前 worker；应用关闭时线程池执行 `shutdownNow()` 并最长等待 30 秒。插件忽略中断时不能被强制终止，并继续占用 worker。handler 返回 `null`、失败 `ServiceResult` 或 `retryable=true` 只记录，不自动重试。非 JVM 致命 `Throwable` 被隔离，仅 `VirtualMachineError` 和 `ThreadDeath` 重新抛出。

当前没有 outbox、持久化重试、宿主投递去重和进程崩溃补偿。`sys_plugin_visibility` 不过滤事件数据，获得 `EVENT_SUBSCRIBE_{eventType}` 即代表可接收该类型全部事件。真实签名 PF4J `EMPLOYEE_HIRED` 探针已覆盖安装、启用、订阅、业务提交后发布、权限与上下文绑定、异步 handler 和安全卸载全链路；其余五类仅覆盖真实业务发布与分发专项。

## 通用调用网关

当前入口为 `POST /api/plugin-gateway/{pluginId}/actions/{actionCode}`，请求体是可选 JSON 对象。网关按以下顺序执行：

当前动作 `POST` 网关的来源校验是附加防线：优先精确校验 `Origin`，仅在 `Origin` 缺失时回退 `Referer`；`Origin` 不得带路径或查询，`Referer` 可带页面路径但不得带 query/fragment，且两者均须通过标准端口归一化后的白名单匹配。缺失、非法、非 HTTP(S)、userinfo、相似域或端口不匹配的来源均拒绝。拒绝返回 HTTP `403`、业务码 `4003`；匿名请求仍由 Spring Security 返回 `401`。全站 CSRF 已由 `SecurityConfig` 的 Cookie/Header 契约覆盖。

来源白名单配置为 `workforce.plugin.gateway.csrf.allowed-origins`，环境变量为 `WORKFORCE_PLUGIN_GATEWAY_CSRF_ALLOWED_ORIGINS`。`application` 默认值仅包含本机 `localhost`/`127.0.0.1`（含本地前端端口）；非本地部署必须显式设置该配置。

1. 先执行上述来源校验（范围仅为当前动作 `POST` 网关）。
2. 查询注册记录并要求状态为 `ACTIVE`。
3. 通过 `PluginLifecycleGuard.tryAcquire` 原子完成“入口开放检查 + 活跃请求计数”，并在 `finally` 中释放。
4. 由宿主绑定 `InvocationContext`，执行插件能力、动作授权和调用者权限校验。
5. 权限通过后才使用 `PluginManagerService.findActionHandler` 触碰 PF4J 扩展并发现动作。
6. 按 `ActionDescriptor.inputSchema` 校验参数后调用 `PluginActionHandler.execute`。
7. 对不存在、状态冲突、权限不足、参数错误和内部异常返回固定 HTTP 状态及 `ServiceResult`，不回传插件异常细节。

当前仍未在 HTTP 网关层执行 `ActionDescriptor.defaultTimeout`，`idempotent` 也只是描述字段，不是自动幂等保证；事件回调的超时和幂等声明约束见上一节。

宿主全局 CSRF 与网关来源校验是两层边界；其他 Session 写接口不依赖该来源白名单，仍需各自完成认证、授权和审计，跨站部署还需单独验证 CORS、SameSite、Secure 和 TLS 终止配置。

## 宿主服务现状

`HostService` 当前是标记接口，宿主通过 `HostServiceRegistry` 注册其具体子接口实现，并以 JDK 动态代理逐次校验：

- 子接口每个业务方法必须声明一个非空 `@RequiresCapability`。
- 首个参数必须是宿主绑定的 `InvocationContext`。
- 调用时上下文中的插件 ID 必须与代理绑定的插件 ID 一致。
- 能力授权以宿主数据库为准，缺失即拒绝。

v0.1 已落地的样板仅有 `EventService` / `DefaultEventService`。旧文档中的 `LeaveServiceImpl`、`LeaveService` 以及其他业务 `HostService` 尚不存在，不应复制为当前 API；后续按真实业务模块逐个定义。

事件桥接边界：`WORKFLOW_APPROVED`、`WORKFLOW_REJECTED`、`EMPLOYEE_HIRED`、`EMPLOYEE_LEFT`、`FILE_UPLOADED`、`ATTENDANCE_EXCEPTION` 均已从真实业务事务接入；真实签名 PF4J 插件已完成 `EMPLOYEE_HIRED` 订阅处理器端到端验证。可靠投递仍受上一节列出的 outbox、重试、队列丢弃和可见范围边界限制。
