# 插件化工作台 - 风险与约束

## 风险清单

| 风险 | 当前控制 | 尚未完成 |
|------|----------|------------|
| PF4J 与 Spring Boot 3.x 兼容 | PF4J Core 3.15.0、单一 `WorkforcePluginManager`、构造器注入 `PluginContext`；v0.1 不创建 Spring 子 Context | 仍只面向可信内部插件，不提供不可信代码隔离 |
| 安装包安全 | RSA 分离签名、宿主计算 SHA-256、`plugin.json` 64KB 上限、安装源复制到宿主快照、迁移临时目录 | JAR 总大小、entry 数、解压上限、全量重复条目拒绝、快照权限隔离仍未完成 |
| 前端动态加载 | `window.__WORKFORCE_HOST__`、IIFE 单文件、SRI、固定 Nginx 路由和最小 CSP，签名清单绑定 `type`/`provider`/SRI；loader 校验注册来源和摘要一致性，脚本 10 秒超时，清单换代与退出会话清理运行时；真实 Chromium 已覆盖正常加载、跨域阻断回退和管理端兼容 | 通用前端产物原子发布、缓存、运行中单插件卸载、样式隔离及更完整 CSP 指令仍需补齐 |
| 生命周期并发 | 单 JVM `synchronized` 生命周期方法和 `PluginLifecycleGuard` 请求排空；真实 hello-plugin 已完成 100 轮串行启停回归，并验证正常 ACTIVE 快照跨两个独立 JVM 恢复 | 多实例锁、恢复所有权、依赖拓扑，以及断电/强制崩溃和中间状态恢复仍未完成 |
| ClassLoader 冲突与释放 | PF4J 独立 ClassLoader；`WorkforcePlugin` final 生命周期在启动失败/停止时逆序关闭已注册资源，失败动作保留重试且阻止重启/卸载；动态资源探针覆盖插件线程、线程内与宿主线程 ThreadLocal、TCCL、最小 JDBC Driver 注册表/CallerSensitive 边界和 ClassLoader 回收；连续 3 个隔离 JDK 17 JVM 的 100 轮完整生命周期进程级 Java heap 中位数增量均 ≤ 16 MiB | 协议无法识别插件未注册的 native/global 资源；未覆盖厂商驱动/连接池后台资源；宿主尚无强制停止超时，仍只面向可信插件；插件级归因、生产长期监控及 native/off-heap/RSS 观测仍未实现 |
| Flyway 冲突与原子性 | 每插件独立 history 表，从 JAR 提取到临时目录执行；最终安装记录字段和已存在 ID 在迁移前预检 | 数据库瞬时失败、多实例并发安装仍可能在迁移后写表失败，MySQL DDL 不能承诺自动回滚 |
| 员工端与管理端权限 | 员工清单按插件状态、类型和“全部/主管/部门/岗位/指定用户”过滤；配置 API 受 `ADMIN_PLUGIN_MANAGE`、全站 CSRF 和事务内脱敏审计保护 | 插件列表、上传、启停、卸载等规划管理 API 及其审计链路仍未实现 |
| 宿主 CSRF | `CookieCsrfTokenRepository`、匿名 `/api/csrf` bootstrap、共享客户端 Cookie/Header 契约、真实协议与双端传输测试 | 跨站部署的 CORS/SameSite/Secure/TLS 验证、强制 token 轮换和 CSRF 403 后自动重放不在 v0.1；bootstrap 失败允许后续新请求重试，各业务接口仍需独立认证、授权与审计 |
| 真实事件链 | `FILE_UPLOADED` 已覆盖员工/管理员普通确认与秒传，仅首次附件引用创建后在事务提交后同步分发 | 同步 handler 会阻塞上传响应且无执行超时；其余五类业务发布点、真实 PF4J 订阅处理器端到端、outbox、持久化重试和崩溃补偿尚未完成 |

## PoC 阻断项（已关闭）

| 原阻断项 | 当前结论 | 边界 |
|----------|----------|------|
| `window.Vue` 不存在 | 已关闭：宿主通过被冻结的 `window.__WORKFORCE_HOST__` 显式提供 Vue API，IIFE 不依赖 `window.Vue` | 仅验证当前 Host SDK 协议；Vue 命名空间本身未冻结 |
| 插件资源没有部署路径 | 已关闭：Nginx 仅开放 `/plugins/{pluginId}/index.js`，Docker 构建已包含 hello-plugin PoC 产物 | 通用安装后发布前端产物仍未实现 |
| 前端清单信任边界 | 已关闭：`type`、`provider`、`frontendSha384` 来自已签名清单，入口按签名 ID 固定派生，hello-plugin 绑定实时 IIFE SHA-384 摘要 | 不等于通用构建、签名、缓存和原子发布链路已完成 |
| ClassLoader 无法释放 | 已关闭：manager 保持可达时，hello-plugin 与动态资源探针均验证 PF4J unload 后 ClassLoader 关闭并进入 `ReferenceQueue`；动态资源探针同时关闭线程、ThreadLocal/TCCL 和最小 JDBC Driver 注册表项 | GC 断言只作有界辅助证据；插件仍须正确注册资源，宿主不隔离恶意代码 |

## 遗留设计问题（后续阶段补齐）

### 升级与回滚
- 升级API、同插件多版本处理、降级限制
- 当前安装存在性检查不区分状态，`UNINSTALLED` 记录会阻止同 ID 重装；重装/替换流程尚未实现
- 旧产物保留、失败回滚策略
- 数据库迁移通常只能前进，不能承诺完整回滚

### 生命周期并发
- 已实现单 JVM 生命周期串行化、入口关闭和最长 30 秒请求排空
- `disable`/`uninstall` 在真实 `PluginLifecycleGuard` 存在活跃请求且排空失败时，均持久化 `ERROR` 和 `error_message=排空超时或中断，需重启`；入口与守卫保持关闭和保留，不执行 stop、unload 或 remove
- “需重启”仅复用现有 `ERROR` 与 `error_message` 表达处置要求，未新增 `restart_required` 字段或独立状态；不承诺重启后自动恢复，也不等同于独立 JVM/进程重启恢复测试
- 已通过真实 hello-plugin 单 JVM 串行 `enable → disable` 100/100 轮：数据库状态、PF4J 状态、动作扩展、请求守卫、wrapper/ClassLoader 身份和卸载关闭均保持一致
- PF4J 启停本身没有执行超时，重复管理请求也没有持久化幂等
- 依赖插件逆序停用
- `restorePlugins()` 已逐插件隔离运行异常；记录 `ERROR` 状态失败时仅记录日志，不中断后续插件恢复
- 已用真实 hello-plugin 验证同一 JVM 内从旧管理器停止并卸载插件、移除旧守卫状态后，以同一数据库记录和 JAR 快照新建 PF4J 管理器可恢复 `ACTIVE` 状态、动作扩展、请求守卫并更换 ClassLoader
- 已通过真实 Spring Boot `ApplicationStartedEvent` 启动两个顺序独立子 JVM：父 JVM 停止/卸载后保留 `ACTIVE` 记录与 `.snapshots` 快照；子 JVM A 自动恢复并验证动作扩展、请求守卫和快照路径，退出后 `updated_at` 不变；子 JVM B 再次恢复并卸载，验证 `UNINSTALLED`、`PluginClassLoader` 关闭、扩展和守卫清理
- 多实例或 `worker` profile 下的恢复所有权、分布式锁尚未设计
- `DISABLING`/`ERROR` 等崩溃中间状态恢复仍未完成；本次独立 JVM 验证不覆盖 OS 重启、断电、强制崩溃、Docker 或多实例锁

### 依赖契约
- 版本范围、循环依赖检测
- 拓扑启动、反向依赖卸载限制

### 宿主兼容性
- 已实现 `sdkVersion`、`minHostVersion`、可选 `maxHostVersion`、`javaVersion` 的安装/恢复校验
- SDK `1.x` 及以上要求同主版本且插件版本不高于宿主；SDK `0.x` 还要求同次版本
- 已校验 PF4J 插件 ID、版本与签名 `plugin.json` 一致，版本字段不信任外部 metadata
- 仍需补充前端协议版本校验和升级/降级策略

### 通用调用网关
- 已实现固定 URL、动作发现、参数 Schema 校验、逐动作权限、生命周期计数和统一错误响应
- `defaultTimeout`、`idempotent` 尚未形成执行约束，事务边界和自动审计仍需补齐
- 当前动作 `POST` 网关已执行 `Origin` 精确白名单校验，且仅在 `Origin` 缺失时回退 `Referer`；拒绝返回 HTTP `403`、业务码 `4003`，匿名请求仍由 Spring Security 返回 `401`
- 来源白名单配置为 `workforce.plugin.gateway.csrf.allowed-origins`，环境变量为 `WORKFORCE_PLUGIN_GATEWAY_CSRF_ALLOWED_ORIGINS`；默认仅本机来源，非本地部署必须显式设置
- 校验范围仅为当前插件动作网关；Origin/Referer 是额外来源防线。宿主全局 SecurityFilterChain 已统一启用 CSRF，其他 Session 写接口不依赖该来源白名单，仍需各自完成认证、授权和审计。

### CSRF防护
- 全站 Spring Security CSRF 已完成：`CookieCsrfTokenRepository`、匿名 `/api/csrf`、无 ignore、所有宿主 unsafe 方法统一 403/401 语义；共享客户端负责双端 bootstrap、Cookie/Header 注入和失败边界。
- 插件配置管理写接口继承全局 CSRF，并已由 `ADMIN_PLUGIN_MANAGE`、管理员认证和事务内脱敏审计保护；不使用动作网关的 Origin/Referer 白名单。
- 当前动作 `POST` 网关的 Origin/Referer 白名单仍保留为附加防线。插件上传、启停、卸载等规划管理路由尚未实现，落地时仍须沿用全局 CSRF、独立授权和审计。
- 跨站部署的 CORS/SameSite/Secure/TLS 验证、强制轮换和自动重放不在本轮范围。

### 真实事件链
- `FILE_UPLOADED` 已接通生产调用点：员工和管理员的普通确认、秒传在首次创建 `sys_attachment_ref` 后，通过 `DomainEventPublisher` 注册提交后事件，再由 `PluginFileUploadedEventListener` 转换并调用 `PluginEventDispatcher`
- 相同待确认票据并发确认、相同 `clientRequestId` 并发秒传和顺序幂等重试均只发布一次；事务回滚不发布。事件 `eventId` 与 `idempotencyKey` 均为 `file-uploaded-{attachmentRefId}`
- 四个顶层上传事务使用 `READ_COMMITTED`：MySQL `REPEATABLE_READ` 下，唯一键冲突后的事务可能仍停留在旧快照，无法读取并发赢家刚提交的票据或附件；唯一约束仍负责裁决赢家，引用数与用量继续使用原子 SQL
- 当前分发是同步、事务提交后、best-effort；插件分发异常会记录完整堆栈且不反向影响已提交文件业务，但没有 outbox、持久化重试或进程崩溃补偿，提交后到分发完成前仍存在丢事件窗口
- `publishEvent`、`@EventListener` 和 `PluginActionHandler.execute` 均在上传请求线程同步执行；慢或卡死的插件不会回滚已提交文件数据，但会延迟或阻塞上传响应，`ActionDescriptor.defaultTimeout` 当前未形成事件 handler 执行约束
- 其余五类真实业务发布点和真实 PF4J 订阅处理器端到端尚未完成；现有分发器、订阅服务和 handler 边界测试不能替代该全链路验证
- 文件配额仍是“先校验、后原子增加”，不同业务请求并发时存在既有的超限窗口；本次隔离级别调整没有扩大或关闭该风险

### 配置安全
- 已实现 `(plugin_id, config_key)` 命名空间、键/类型/大小/数量校验、`version` 乐观锁和删除墓碑代际，删除重建不会复用旧版本；同时具备 `ADMIN_PLUGIN_MANAGE`、全站 CSRF 和创建/更新/删除事务内脱敏审计
- `SECRET` 使用 AES-256-GCM、随机 12 字节 nonce、128 位 tag，AAD 绑定插件 ID 与配置键；管理 API 不返回明文或密文，插件只通过绑定命名空间的只读 `PluginConfig` 解密读取
- 所有敏感 PUT 均要求当前主密钥可用；`value=null` 的元数据更新还必须成功解密原密文，失败返回 `422`，提交新值可用当前密钥重设
- 主密钥必须是 `WORKFORCE_PLUGIN_CONFIG_ENCRYPTION_KEY_BASE64` 提供的 32 字节 Base64 值；数据库与原主密钥需分开备份并成对恢复
- 当前无 key ID、多密钥、自动轮换、重加密或 KMS；密钥替换或丢失会使既有敏感配置不可解密
- 已签名 `plugin.json` 不提供配置 schema；宿主尚无 schema 注册/校验、批量配置定义和管理端配置编辑界面
- `requiresRestart` 仍只是元数据，不自动停用、重启或记录待重启状态

### 签名信任链
- 已实现 X.509 编码 RSA 公钥白名单、安装/恢复复验；白名单在应用启动时读取，新增、轮换或删除签名者均需重启生效
- 重启后，新安装和启动恢复会拒绝已删除签名者；仍需补充密钥轮换流程和旧版本回放保护

### 安装包信任边界
- 安装时已先复制到 `pluginsRoot/.snapshots`，后续验签、读取清单、PF4J、Flyway 和持久化统一使用快照；上传源后续被替换不会影响安装
- 快照不是内容寻址，也没有超出 OS 权限的不可变保护；同一账号可篡改，恢复阶段验签后再次打开快照仍有 TOCTOU 边界
- `type`、`provider`、`frontendSha384` 已来自签名清单，`frontendEntry` 由宿主按签名 ID 固定派生；外部同名 metadata 不参与最终记录，旧 JAR 无回退且必须重新构建、签名
- 恢复时在 PF4J 加载前比较 `type`、`provider`、`frontendEntry`、`frontendSha384`，任一漂移均 fail closed 并标记 `ERROR`；`provider` 只是签名声明，真实签名者仍以 `signerId` 白名单为准
- JAR 总大小、entry 数、单 entry 大小、迁移解压总量和 SQL 语句限制尚未实现

### 安装原子性
- 已在 PF4J/Flyway 前构建最终 `PluginRow`，校验字段长度、签名大小并拒绝检查时已存在的插件 ID，确定性的字段超长和已知重复 ID 不再留下迁移
- 当前仍先执行 Flyway，再插入 `sys_plugin`；数据库瞬时失败或多实例并发安装竞态仍可能使迁移及插件 history 保留
- 仍需数据库安装占位状态和跨实例协调，不能依赖 `exists` 检查或 PF4J unload 回滚数据库

### 前端隔离与卸载
- 错误边界、路由回退和宿主内部会话清理已实现；退出登录后整页重载以清除同 Realm 顶层副作用；全局 Host SDK 不暴露注销或清理 API
- 当前 CSP 只限制脚本来源，不隔离已允许的同源插件；SRI 只保证产物完整性，插件仍与宿主共享 Realm 和页面权限
- 插件脚本加载失败时当前只移除入口并回退 OA，没有可见错误提示或脚本级重试；工作台重试只覆盖组件工厂和渲染错误
- 运行中单插件停用后的脚本卸载、CSS 命名空间、样式和事件监听清理仍未实现

### 缓存策略
- 当前 PoC 对插件脚本使用 `no-store`；内容哈希 URL、不可变缓存和清单禁缓存尚未设计
- 同会话内不同摘要、外部预注册和失效旧脚本已 fail closed；跨部署原子发布与缓存一致性仍未完成

### 部署链路
- Nginx 精确插件脚本路由与 hello-plugin Docker 构建 PoC 已完成
- 安装服务如何把任意插件前端产物原子发布到 web 容器尚未实现；当前不是 server-storage 动态挂载方案

### ClassLoader释放
- 已用真实 hello-plugin 验证 manager 保持可达时，PF4J `PluginClassLoader` 在 unload 后关闭，manager 无插件/ClassLoader、扩展为空，并进入 `ReferenceQueue`
- `WorkforcePlugin` 只允许覆盖 `onStart` / `onStop`，长期资源通过 `registerCleanup(AutoCloseable)` 注册；启动失败和停止均逆序执行全部清理，只有成功项移出队列，失败项保留重试并阻止重启/卸载，异常保留主因与 suppressed
- `WorkforcePluginManager` 在构造前校验主类继承关系，卸载前校验目标及依赖者；Spring 关闭逐个处理 active/unresolved 插件，单个清理失败不跳过其他插件
- 动态资源探针在宿主线程池保持存活时验证 `ThreadLocal finally remove()`，并验证插件线程 interrupt/有界 join、线程内 ThreadLocal、TCCL 释放、CallerSensitive 最小 JDBC Driver 插件侧注销和 ClassLoader 回收；不等同于厂商驱动或连接池验收
- 安装与恢复会记录加载前插件集合；PF4J 在返回 ID 前因依赖解析失败时，宿主按 JAR 路径识别本次新增 wrapper，并在不卸载依赖者、不重新解析全局依赖的条件下清理；真实缺失依赖 JAR 的安装、恢复和既有 unresolved 依赖者保留测试均已覆盖
- 安装失败时只有 PF4J 确认清理成功才删除未持久化快照；清理返回失败或抛异常时保留快照并暴露 suppressed 错误，需重启后处置
- 协议不能自动发现未注册的 native/global 资源，也不能清理其他线程中未使用 `finally remove()` 的 ThreadLocal；插件停止仍依赖插件侧有界等待，宿主级强制超时未实现
- 已用连续 3 个隔离 JDK 17 子 JVM 验证 20 轮预热后 100 轮完整加载、启动、停止和卸载；固定 256 MiB SerialGC 下，基线与末段各 3 次有界 GC 后进程级已用 Java heap 中位数增量均不超过 16 MiB，120/120 个探针 ClassLoader 均回收

### 可观测性
- 插件健康状态、启动耗时、调用量、错误率
- 活动请求数、最后失败原因、独立日志和告警指标
- 当前堆增长阈值只存在于隔离测试 JVM，不会在生产进程调用 `System.gc()`，也没有接入长期告警
- 该回归仅比较固定负载和固定 JVM 配置下、有界 GC 后的进程级已用 Java heap 中位数；不提供插件级内存归因，不证明单个插件“零泄漏”，不覆盖 native/off-heap/RSS，也不构成生产长期监控或告警

### 验收量化
- 已量化单插件单 JVM 串行启停 100/100 轮；另以连续 3 个隔离 JDK 17 子 JVM 验证 100 轮完整生命周期后进程级 Java heap 中位数增量均 ≤ 16 MiB。该结果没有插件级归因；停止超时、加载耗时及生产长期内存监控阈值仍未建立
- 最大包大小、故障恢复时间及权限测试矩阵
