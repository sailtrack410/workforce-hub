## 2026-05-02 docs 全量分类重构与目录索引收口

### 改动背景

虽然上一轮已经把审查文件和开发日志从 `docs/` 根目录剥离出来，但随着产品文档、架构文档、开发规划文档和 API 文档继续增加，`docs/` 根目录仍然存在大量平铺文件。

这会带来三个实际问题：

- 新人第一次进入仓库时，很难一眼看出“哪类文档该去哪找”
- 后续继续新增文档时，容易再次回到“先扔根目录再说”的状态
- 同一个主题的文档没有被聚合，后面做比赛材料、交付材料或模块文档拆分时成本会越来越高

因此这一步要把 `docs/` 从“局部归档”继续推进到“全量分类”，让根目录只保留分类目录与总索引。

### 本次目标

- 为 `docs/` 建立稳定的一级分类目录
- 把根目录散落的正式文档全部迁入对应类别
- 为 `API` 文档建立按模块继续扩展的子目录结构
- 增加 `docs/README.md` 作为统一入口
- 全量校准旧路径引用，避免目录移动后正文仍指向旧位置

### 执行过程

#### 1. 设计一级分类

本轮最终确定的一级分类为：

- `docs/产品与业务/`
- `docs/架构与设计/`
- `docs/开发规划/`
- `docs/API与测试/`
- `docs/开发日志/`
- `docs/审查/`
- `docs/申报材料/`

**意义**：

- 让“业务总纲、技术设计、推进计划、接口资产、过程记录、申报材料”各自有固定落点
- 后续继续加文档时，优先是“找分类目录”，而不是“再往根目录塞一个文件”

#### 2. 迁移散落文档

本轮把原先直接放在 `docs/` 根目录的文档分流到对应类别，例如：

- `docs/产品与业务/平台总导图.md`、`docs/产品与业务/团队协作平台.mm`、`docs/产品与业务/项目确认记录.md` 完成归类收口
- `docs/架构与设计/技术栈与架构方案.md`、`docs/架构与设计/后端工程骨架说明.md`、`docs/架构与设计/核心表结构草图.md`、`docs/架构与设计/状态机设计.md`、`docs/架构与设计/权限矩阵.md`、`docs/架构与设计/接口与事件清单.md` 完成归类收口
- `docs/开发规划/开发流程总览.md`、`docs/开发规划/开发落地清单.md` 完成归类收口
- `module-org` 的 API 文档与测试用例迁入 `docs/API与测试/module-org/`

**意义**：

- 让同一主题的文档物理上聚合在一起
- 为后续 `module-auth`、`module-workflow`、`module-im` 等 API 文档预留统一扩展方式

#### 3. 增加总索引并明确维护约定

新增：

- `docs/README.md`

在索引中明确约定：

- `docs/` 根目录原则上只保留 `README.md` 和分类目录
- 新 API 文档统一放入 `docs/API与测试/<module>/`
- 新日志统一写入 `docs/开发日志/`
- 新审查统一写入 `docs/审查/`

**意义**：

- 把“这次整理结果”变成可持续执行的目录约束
- 避免过几轮开发后，大家只记得目录改过，但不记得应该怎么继续维护

#### 4. 校准全文引用与说明口径

对 `docs/` 目录与测试脚本中的旧文档路径做了一轮统一替换，把原先的根目录路径更新为新的分类路径，并补齐总览文档里的入口指向。

同时清理了 `docs/.DS_Store` 和 `docs/申报材料/.DS_Store` 这类无效噪音文件。

**意义**：

- 防止“文件已经搬走，但正文还写旧路径”
- 减少仓库里与业务无关的 Finder 生成文件

### 当前结果

- `docs/` 根目录已不再保留散落的业务/设计文档

## 2026-05-01 本机开发环境准备

### 改动背景

进入 `module-auth` 与后续业务模块联调前，需要先把本机最小运行环境补齐。排查结果显示：机器上虽然已有 MySQL 服务和多个 JDK 版本，但 `mvn` 实际跑在 JDK 25、Redis 尚未安装、MySQL 客户端命令也没有进入默认 `PATH`，直接影响后端启动与日常联调效率。

### 本次目标

- 让当前工程的 `mvn` 稳定使用 `JDK 17`
- 安装并启动本机 `Redis`
- 确认本机 `MySQL` 服务可用并创建业务库 `workforce_hub`
- 明确邮箱凭证只作为运行时环境变量使用，不落入仓库文件

### 执行过程

#### 1. 盘点本机现状

先检查 `mvn -version`、`java -version`、`/usr/libexec/java_home -V`、`redis-server`、`redis-cli`、`mysql` 等命令，目的是确认当前缺的到底是“软件没装”，还是“软件已装但环境变量没接上”。

**意义**：
- 避免误装重复组件
- 把问题分成“版本问题”“服务问题”“PATH 问题”三类分别处理

#### 2. 收口 Maven 到 JDK 17

发现 `JDK 17` 和 `JDK 21` 都已安装，但 `mvn` 实际跑在 `JDK 25`，会被工程里的 JDK 校验拦住。因此新增用户级 `~/.mavenrc`，让 Maven 启动时统一通过 `/usr/libexec/java_home -v 17` 解析 `JAVA_HOME`，不再依赖写死的具体 JDK 安装目录。

**意义**：
- 解决当前项目的 Maven/JDK 版本不一致问题
- 比直接写死 `/Users/.../ms-17.0.18/...` 更稳，JDK 17 小版本升级后仍可继续使用

#### 3. 安装并启动 Redis

通过 `Homebrew` 安装 `Redis Open Source`，实际安装版本为 `8.6.2`，随后用 `brew services start redis` 拉起后台服务，再用 `redis-cli ping` 验证返回 `PONG`。

**意义**：
- 为 `Spring Session + Redis`、邮箱验证码、登录失败频控提供运行基础
- 后续本地重启机器后 Redis 仍可随登录自动拉起，减少手工启动成本

#### 4. 定位 MySQL 安装来源并验证服务状态

检查后发现当前 MySQL 不是 Homebrew 版本，而是官方安装包版本，实际路径在 `/usr/local/mysql`。继续确认 `mysqld` 进程已经运行，说明数据库服务本身可用，只是 `mysql` 命令未进入默认 `PATH`。

**意义**：
- 解释了为什么“明明装了 MySQL，但终端里 `mysql` 命令不存在”
- 后续如果要补环境说明，可以明确区分“服务已启动”和“客户端命令不可直用”这两个层面

#### 5. 创建业务库 `workforce_hub`

使用 `/usr/local/mysql/bin/mysql` 显式连接本机 MySQL，按项目默认字符集创建 `workforce_hub`，随后通过 `SHOW DATABASES LIKE 'workforce_hub'` 回查成功。

**意义**：
- 让 Spring Boot 启动后能直接连到目标主业务库
- 为 Flyway 初始化 69 张业务表提供落库目标

#### 6. 邮件凭证处理原则

本机已确认后续会使用网易邮箱 SMTP，但凭证只作为运行时环境变量使用，对应 `MAIL_HOST`、`MAIL_PORT`、`MAIL_USERNAME`、`MAIL_PASSWORD`。本轮不把任何真实密码写入仓库文件、设计文档或提交记录。

**意义**：
- 保持本机联调可行
- 同时避免把真实密钥固化进代码库

### 当前结果

- `mvn -version` 已切换为 `JDK 17`
- `Redis 8.6.2` 已安装并成功启动
- `redis-cli ping` 返回 `PONG`
- 本机 `MySQL` 服务已运行
- `workforce_hub` 数据库已创建

### 环境变更清单

- `~/.mavenrc`
  - 新增 Maven 专用 `JAVA_HOME` 解析，统一固定到 `JDK 17`
- Homebrew `redis`
  - 安装 `Redis Open Source 8.6.2`
  - 启动为本机后台服务
- 本机 MySQL
  - 确认服务进程已运行
  - 新建业务库 `workforce_hub`

### 已知待补项

- `mysql` 客户端命令尚未进入默认 `PATH`，当前仍需使用 `/usr/local/mysql/bin/mysql`
- 还没有一份正式的“本机启动环境变量清单 / `.env.example`”
- `PostgreSQL + pgvector`、`MinIO` 仍未安装，后续推进 `module-kb`、文件上传链路时再补

## 2026-05-01 JDK 基线收口

### 改动背景

在继续校准 `module-auth` 骨架文档时，发现虽然工程在 JDK 17 下可稳定编译，但当前机器默认 `mvn` 实际跑在 JDK 25，上来仍会因为 Lombok 与 `javac` 兼容性问题直接失败。考虑到本项目后续以 Docker 方式交付，没必要同时维护 17/21 双基线，直接固定一个 JDK 版本更稳妥。

### 本次决定

- 当前工程、本地开发、CI、Docker 镜像统一固定为 `JDK 17`
- 不再把 `JDK 21` 作为当前交付承诺范围，避免“本地一套、容器一套”
- 后续如需升级到更高版本 JDK，再单独做一轮依赖兼容性验证

### 本次改动

- `server/pom.xml`
  - 增加 `maven-enforcer-plugin`
  - 在 `validate` 阶段强制校验 Java 版本为 `[17,18)`
  - 若使用错误 JDK（如 25），直接给出明确错误信息，而不是编译到一半才报 Lombok / `javac` 兼容问题
- `docs/架构与设计/技术栈与架构方案.md`
  - 后端主体 JDK 口径由 `Java 21` 收口为 `Java 17`
- `docs/产品与业务/项目确认记录.md`
  - 主体技术栈中的 Java 版本由 `21` 收口为 `17`
- `docs/开发日志/工程与基础设施.md`
  - 将此前“17/21 双兼容”的表述改为“当前正式基线为 JDK 17”

### 验证结果

- 默认 Maven（当前机器实际使用 JDK 25）执行 `mvn -DskipTests clean compile`
  - 现在会在 `maven-enforcer-plugin` 阶段直接失败，并提示“当前项目固定使用 JDK 17”
- 显式切到 `JDK 17` 后执行 `mvn -DskipTests clean compile`
  - 构建通过

## 2026-05-02 集成测试独立测试库隔离

### 改动背景

第 14 审已经明确指出：`module-org` 的自动化测试虽然覆盖面在增加，但仍然直接写本地主业务库 `workforce_hub`。随着第二批写侧接口和组织领域事件都已经接入测试，这个边界继续保留下去会带来两个问题：

- 本地开发数据会被测试持续污染，排查问题时很难分清“这是业务真实数据”还是“这是上一次测试残留”
- 一旦换到全新数据库环境，测试上下文还会顺带拉起 Flowable，而新测试库里并没有 `ACT_*` 引擎表，导致 Spring Boot 启动阶段直接失败

因此这一轮的目标不是再加新业务接口，而是把“测试跑在独立数据库上”这件基础设施能力正式补齐。

### 本次决定

- `module-org` 集成测试默认连接独立测试库 `workforce_hub_test`
- 测试库连接优先读取 `TEST_DB_*`，未显式配置时再回退到 `DB_*`
- 测试支撑层在本轮直接排除整套 Flowable 自动配置，避免组织模块联测被流程引擎表结构耦住
- 保持正式运行时配置不变，本轮只收口测试环境，不提前改动 `module-workflow` 的真实边界

### 本次改动

#### 1. 给测试环境单独补齐数据库变量入口

- `.env.example`
  - 新增 `TEST_DB_HOST`
  - 新增 `TEST_DB_PORT`
  - 新增 `TEST_DB_NAME=workforce_hub_test`
  - 新增 `TEST_DB_USER`
  - 新增 `TEST_DB_PASSWORD`

**意义**：
- 让“主业务库”和“测试库”在变量层面就能明确分开
- 后续无论本机联调还是 Docker / CI，都有清晰的注入位点，不需要再把测试连接硬编码在代码里

#### 2. 测试数据源切到独立测试库，并允许按需自动建库

- `server/src/test/java/com/workforcehub/support/LocalIntegrationTestSupport.java`
  - JDBC URL 默认库名改为 `workforce_hub_test`
  - 增加 `createDatabaseIfNotExist=true`
  - 测试数据源优先读取 `TEST_DB_*`，没有时回退到 `DB_*`

**意义**：
- 第一次在新机器上跑测试时，不需要手工先建测试库
- 默认测试数据不再落回主业务库，降低误污染开发数据的概率

#### 3. 在种子脚本前先清空业务表，确保重复执行可复位

- `LocalIntegrationTestSupport`
  - 新增 `resetBusinessTables()`
  - 在装载 `seed_module_org_smoke_data.sql` 之前，先清空：
    - `hr_employee_event`
    - `auth_user_account`
    - `org_department_leader`
    - `org_user`
    - `org_position`
    - `org_department`
    - `admin_user`

**意义**：
- 让同一批集成测试可重复执行，不依赖“上一次数据库正好是干净的”
- 写侧接口、登录链路、领域事件断言都能在同一测试库里反复回放

#### 4. 测试环境显式排除 Flowable 自动配置

- `LocalIntegrationTestSupport`
  - 通过 `spring.autoconfigure.exclude` 排除 Flowable 相关自动配置
  - 包括 `ProcessEngine`、`Idm`、`Cmmn`、`Dmn`、`EventRegistry`、`FlowableSecurity` 等测试不需要的配置

这里的核心判断是：

- `module-org` 当前测试并不依赖 Flowable Bean
- 如果为了让组织模块联测跑起来而在测试库补整套 `ACT_*` / `FLW_*` 表，会把测试基础设施再次绑回工作流引擎
- 这一步更合理的做法是让“谁需要 Flowable，谁在自己的测试里显式打开它”

**意义**：
- 让组织模块的联测真正只依赖“组织模块本身需要的设施”
- 为后续 `module-workflow` 单独设计更贴近真实工作流场景的测试支撑留出边界

### 验证结果

- `cd server && mvn -DskipTests compile`
  - 通过
- `cd server && mvn -Dtest=ModuleOrgApiIntegrationTest,ModuleOrgWriteApiIntegrationTest test`
  - 通过
- 本轮验证确认：
  - Flyway 已能在 `workforce_hub_test` 上完成业务表初始化
  - `module-org` 查询链路、写侧链路、组织领域事件断言都可在独立测试库上跑通
  - 测试启动不再依赖主业务库已有的 Flowable 历史表

### 这一步解决了什么

- 解决了“测试写主库”的环境污染问题
- 解决了“新测试库因为缺少 Flowable 表而起不来”的启动阻塞
- 让后续继续扩写 `module-org` 自动化用例时，环境边界更可控

### 仍然保留的边界

- 当前清表逻辑仍是显式表名单；后续 `module-org` 再新增写表时，需要同步把对应表纳入复位范围
- `module-workflow` 后续如果要做真实 Flowable 联测，不应直接沿用这一套“禁用 Flowable”的测试支撑，而应单独建立 workflow 专属测试基线
