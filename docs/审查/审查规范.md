# 审查规范 大厂级严格版

本文定义 `docs/审查` 目录下所有审查文件的统一标准。目标不是“看起来审过”，而是用接近大厂生产变更评审的强度，识别正确性风险、安全风险、数据一致性风险和长期维护成本，避免代码为了修问题而补丁套补丁。

---

## 一、审查基本原则

### 1. 风险优先

审查优先找会导致线上事故、越权、数据错账、状态机错乱、并发重复、迁移失败、回滚困难的问题。格式、命名、局部风格只在影响可维护性时记录。

### 2. 证据驱动

每个问题必须能落到具体文件、方法、SQL、接口、迁移或测试缺口。不能只写“可能有问题”，必须说明：

- 触发条件
- 失败路径
- 影响范围
- 为什么现有代码或测试挡不住
- 推荐修复方向

### 3. 不用测试通过替代审查

测试通过只证明已覆盖路径没有失败，不能证明未覆盖的并发、权限、幂等、回滚、历史数据迁移、生产配置都正确。审查必须主动找测试未覆盖的边界。

### 4. 不鼓励补丁堆叠

发现问题时优先建议收口边界、修正模型、补足状态机或拆清职责。避免建议在已有混乱逻辑上继续叠特殊分支。

### 5. 尊重当前架构但不迁就错误边界

第一版可以接受阶段性简化，但不能接受会污染数据、破坏权限、制造不可恢复状态的设计。阶段性留空必须在文档和接口语义上明确。

## 二、审查准入要求

开始审查前必须确认以下信息：

| 项目 | 要求 |
| --- | --- |
| 提交边界 | 明确 base commit、head commit、提交列表和每个提交主题 |
| 落点目录 | 审查文件必须写入 `/Users/sailtrack/工程文件/java_web/workforce-hub/docs/审查` |
| 现有编号 | 先读取 `docs/审查/README.md`，确认下一个审查编号，不能猜编号 |
| 工作区状态 | 读取 `git status --short`，识别用户已有改动，不覆盖、不回滚 |
| 历史审查 | 读取最近相关审查文件，复核旧问题是否收口，避免重复报同一问题 |
| 差异范围 | 使用 `git log`、`git diff --name-status`、`git diff --stat` 确定影响模块 |

推荐命令：

```bash
git status --short
git log --oneline --reverse <base>..HEAD
git diff --name-status <base>..HEAD
git diff --stat <base>..HEAD
```

## 三、强制审查维度

### 1. 正确性

必须检查：

- 核心业务流程是否能完整闭环
- 状态流转是否只允许合法迁移
- 异常路径是否会留下半成品数据
- 响应结果是否真实反映数据库状态
- 读模型和写模型是否一致
- 历史状态、删除态、过期态是否被正确过滤

高风险信号：

- 先读后写但没有条件更新或锁
- 状态更新不检查当前状态
- 写入成功但后续外部副作用失败无补偿
- 异常被吞掉后返回成功
- 业务字段由客户端传入但服务端不校验可信性

### 2. 权限与越权

必须检查：

- 当前用户是否只能访问自己的资源
- 管理员接口是否只允许管理员路径和管理员身份
- 业务附件、审批、组织、知识库等 ownerType 是否有对应业务授权
- 下载、预览、删除、恢复、导出是否复核权限
- 票据、链接、回调是否绑定申请人、资源和过期时间

阻断级信号：

- 只校验 ID 存在，不校验归属
- 只校验上传人，不校验业务 ownerType
- 低权限接口能操作高权限业务归档
- 下载票据可被非申请人或非参与人使用

### 3. 并发、幂等与重试

必须检查：

- 重复请求是否生成重复业务记录
- 并发确认、并发审批、并发下载是否有唯一约束或条件更新
- 外部系统回调是否支持重复投递
- 任务重试是否会重复扣减、重复发待办、重复启动流程
- 幂等键是否覆盖业务唯一性，而不是只靠先查再写

高风险信号：

- `SELECT` 判断后再 `INSERT/UPDATE`，但没有唯一键、行锁或条件更新
- 回调接口没有幂等结果语义
- 同一个业务单据可启动多个流程实例
- 同一个清理明细可被多个任务重复处理

### 4. 事务与外部副作用

必须检查：

- 数据库事务和对象存储、消息、邮件、Flowable、Agent 调用的边界是否清楚
- 外部副作用成功、数据库回写失败时是否可恢复
- 数据库提交成功、外部副作用未执行时是否有补偿任务
- 独立事务是否只用于必要的状态持久化

高风险信号：

- 事务内直接执行不可回滚的外部删除
- 外部调用发生在状态抢占之前
- 物理删除失败只记录日志，不进可重试账本
- 任务运行记录和任务明细会随业务异常一起回滚

### 5. 数据库迁移与数据模型

必须检查：

- Flyway 迁移是否只新增新版本，不修改已执行旧版本
- 唯一约束是否能覆盖真实业务唯一性
- MySQL `NULL` 唯一键语义是否被正确处理
- JSON、枚举、状态字段是否有清晰边界
- 软删除唯一键是否会阻断恢复或制造重复
- 新表是否有必要索引和查询路径

阻断级信号：

- 修改历史迁移导致 checksum mismatch
- 依赖 MySQL `NULL` 唯一键保证全局唯一
- 状态字段混入决策枚举或动作类型
- 运行时保存了版本快照，但执行时仍取最新版本

### 6. API 契约

必须检查：

- 文档、测试、Controller、Service 返回语义是否一致
- URL 返回后是否有实际执行入口
- 错误码是否区分无权限、资源不存在、状态冲突、参数错误
- 分页、过滤、排序是否有边界和默认值
- 接口是否泄露内部实现字段

高风险信号：

- 文档写已实现，代码只有字符串占位
- 测试只断言 URL 包含路径，不验证执行语义
- `403` 和 `404` 混用导致枚举资源存在性
- 列表接口缺少当前用户过滤

### 7. 测试质量

必须检查：

- 是否有红灯测试证明问题真实存在
- 正向、负向、边界、并发、重复请求是否覆盖
- 测试基类是否清理全部业务表和审计表
- 测试是否只靠历史数据 `COUNT >= N` 误报通过
- 是否验证数据库状态，而不只验证 HTTP 200

高风险信号：

- 只测 happy path
- 测试绕过真实鉴权、真实事务或真实流程引擎
- 并发问题没有并发测试或唯一约束兜底
- 测试数据清理遗漏导致顺序依赖

### 8. 可维护性

必须检查：

- 单个 Service 是否承担过多职责
- Repository 是否混合多个聚合的 SQL
- DTO、Row、Entity 是否边界清楚
- 是否复制审计、JSON 拼接、状态判断、权限判断
- 是否出现同名薄封装导致未来遗漏
- 新模块是否直接依赖另一个模块的内部实现

需要记录的信号：

- 单类超过约 500 行且职责继续扩张
- 一个方法同时做权限、状态机、外部调用、审计、DTO 转换
- 多个服务手写同一种审计 JSON
- 业务模块直接使用其他模块内部 Row、Repository、StorageProvider

## 四、问题严重程度标准

| 等级 | 名称 | 定义 | 处理要求 |
| --- | --- | --- | --- |
| P0 | 阻断 | 会导致服务无法启动、迁移失败、主流程不可用、数据大面积损坏、明显高危越权 | 必须立即修复，不能进入下一节点 |
| P1 | 重要 | 会在真实并发、权限、重试、回滚、生产配置下造成数据不一致、越权、重复扣减、流程错乱 | 当前阶段必须优先处理，不能长期带病扩展 |
| P2 | 建议 | 不一定立即出事故，但会造成维护成本快速上升、语义不清、测试保护不足、后续扩展困难 | 应排入近期治理 |
| P3 | 轻微 | 局部命名、文档细节、低风险重复，暂不影响行为 | 可记录但不应稀释重点 |
| 已处理 | 已收口 | 历史审查问题已被当前提交实质修复，并有代码或测试证据 | 在复核区说明，不再作为新风险重复报 |

严禁把 P1 写成“建议”来降低风险表达。只要可能导致越权、错账、重复流程、不可恢复状态，就按 P1 起评。

## 五、审查文件格式

新增审查文件统一使用：

```text
第N审_主题.md
```

文件结构必须包含：

```markdown
# 第 N 审 主题

- 审查日期：YYYY-MM-DD
- 审查提交：
  - `commit_sha`（提交说明）
- 审查范围：`path`、`path`
- 审查目标：说明本轮重点和不做什么

---

## 第一部分：提交内容概览

## 第二部分：已收口问题复核

## 第三部分：本轮新增正确性风险

## 第四部分：冗余与可维护性隐患

## 第五部分：验证与未验证项

## 第六部分：处理优先级建议

## 第七部分：阶段性结论
```

如果本轮没有历史问题复核，可以把第二部分改为“当前没有发现的阻断问题”，但不能省略风险和维护性分析。

## 六、单条问题写法

每条问题必须用表格记录：

| 字段 | 要求 |
| --- | --- |
| 序号 | `2-1`、`3-1` 等稳定编号 |
| 问题位置 | 文件、类、方法、SQL、迁移名，必要时写行号 |
| 问题描述 | 用一段话说明触发条件、失败路径、影响范围 |
| 严重程度 | P0/P1/P2/P3 或中文“阻断/重要/建议/轻微” |
| 优化方案 | 给方向，不要求写补丁，但必须能指导正确修复 |

问题描述必须避免以下写法：

- “建议优化一下”
- “这里可能有风险”
- “后续注意”
- “代码比较乱”

应该写成：

- “当两个回调并发进入时，都可能读到 `PENDING`，随后各自启动流程实例，因为当前更新没有条件抢占，也没有唯一约束。”
- “员工接口只校验上传人，不限制 `owner_type=PERSONAL_FILE`，因此申请人可以通过个人文件删除接口删除 `WF_REQUEST` 审批归档附件。”

## 七、阻断规则

出现以下任一情况，审查结论必须明确“不建议进入下一开发节点”：

- 存在 P0 问题
- 存在未处理的高风险越权
- 核心状态机并发下可重复执行
- 业务账本可能错账且无修复脚本或补偿路径
- 数据库迁移在空库或历史库上不可重复执行
- 外部副作用失败后无可观测、无重试、无人工恢复路径
- 文档宣称已实现但接口无法执行

如果只是第一版暂未实现某能力，必须判断它是否影响当前承诺的闭环。影响当前闭环则算风险，不影响则记录为后续事项。

---

## 八、验证要求

审查文件必须写清楚执行过和未执行的验证。

推荐验证：

```bash
git diff --check -- docs/审查/新增审查文件.md docs/审查/README.md
mvn -DskipTests compile
mvn -Dtest=相关测试类 test
```

如果不运行测试，必须写明“本轮是静态审查，没有重跑 Maven 测试”。不能暗示测试通过。

如果全仓 `git diff --check` 因历史文件失败，必须区分：

- 本轮新增文件是否通过
- 失败是否来自既有文件

## 九、README 维护规则

每新增一份审查文件，必须更新：

```text
docs/审查/README.md
```

要求：

- 规范文件放在“审查规范”区域
- 轮次文件放在“当前清单”区域
- 不重排无关历史条目
- 不改动不属于本轮的审查文件

---

## 十、审查边界纪律

除非用户明确要求修代码，否则审查任务只允许：

- 新增审查文件
- 更新 `docs/审查/README.md`
- 执行只读命令和必要验证命令

禁止：

- 修改业务代码
- 为了让审查结论变好临时补补丁
- 回滚用户已有改动
- 删除或重写历史审查文件
- 用新审查覆盖旧审查编号

---

## 十一、大厂级审查的最低结论标准

一份合格审查文件至少要做到：

- 能让开发者按优先级修问题
- 能让负责人判断是否允许进入下一节点
- 能让后续审查复核旧问题是否收口
- 能解释为什么某问题是 P1，而不是泛泛建议
- 能区分“功能未做”“功能做了但不正确”“功能正确但不好维护”
- 能把当前提交放进整个模块演进路径里判断，不只看局部 diff

审查不是验收表，也不是代码风格检查。审查的核心价值是提前暴露生产事故路径，并推动代码边界变清楚。
