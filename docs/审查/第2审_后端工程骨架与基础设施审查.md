# 第 2 审 后端工程骨架与基础设施审查

- 审查日期：2026-05-01
- 审查范围：`docs/架构与设计/后端工程骨架说明.md`、`server/pom.xml`、`server/src/main/resources/application.yml`、`server/src/main/resources/db/migration-pg/V1__init_vector_schema.sql`、`server/src/main/java/com/workforcehub/common/response/R.java`
- 审查目标：识别后端工程骨架在数据库迁移、依赖选型、安全链路、统一响应和文档一致性上的阻断性与重大问题，判断其是否适合继续承接后续业务模块开发

---

## 第一部分：逻辑审查

### 一、数据库与迁移

| 序号 | 问题位置 | 问题描述 | 严重程度 | 优化方案 |
| --- | --- | --- | --- | --- |
| 1-1 | `server/src/main/resources/db/migration-pg/V1__init_vector_schema.sql` | PostgreSQL 向量库迁移脚本在列定义中直接使用了 `COMMENT '...'`，这是 MySQL 语法，不是 PostgreSQL 语法。脚本按当前内容执行会直接失败，导致向量库初始化被卡死。 | 阻断 | 删除列定义中的 `COMMENT '...'` 写法，改为表创建完成后单独使用 `COMMENT ON COLUMN ... IS '...'`。 |
| 1-2 | `server/src/main/resources/application.yml` | 项目已经启用 Flyway 管理 MySQL 迁移，但同时又把 `flowable.database-schema-update` 设成了 `true`。这意味着 Flowable 可以绕过迁移脚本直接改库，和“所有结构变更走 Flyway”原则冲突。 | 重大 | 明确数据库治理唯一入口。若主业务库和 Flowable 表都纳入迁移体系，则关闭 `flowable.database-schema-update`；若暂时保留 Flowable 自管，也应与业务库迁移策略明确隔离，避免双轨改库。 |

### 二、安全与认证链路

| 序号 | 问题位置 | 问题描述 | 严重程度 | 优化方案 |
| --- | --- | --- | --- | --- |
| 2-1 | `server/pom.xml` | 项目已引入 `spring-boot-starter-security`，但当前代码中没有任何 `SecurityFilterChain`、`AuthenticationEntryPoint` 或 API 风格安全配置。这样后续一接 Controller，就会回落到 Spring Security 默认表单登录与默认用户行为，和员工端/后台端基于 Session 的 JSON API 预期不一致。 | 重大 | 尽快补最小安全骨架：自定义 `SecurityFilterChain`、关闭默认表单登录、明确未登录/无权限时返回 JSON、为员工端与后台端预留会话鉴权扩展位。 |

### 三、依赖与组件边界

| 序号 | 问题位置 | 问题描述 | 严重程度 | 优化方案 |
| --- | --- | --- | --- | --- |
| 3-1 | `server/pom.xml` | 当前引入的是 `flowable-spring-boot-starter` 总包，而不是仅覆盖流程审批所需的精简组件。这样会额外带入 app/cmmn/dmn/form/content 等整套依赖与引擎能力，放大启动体积、依赖下载量和库表面。 | 重大 | 根据当前产品边界收窄为最小必需 Flowable 组件，只保留审批流程真正需要的 starter 或模块依赖，避免过早把不打算启用的引擎一并带入。 |

### 四、统一响应与可观测性

| 序号 | 问题位置 | 问题描述 | 严重程度 | 优化方案 |
| --- | --- | --- | --- | --- |
| 4-1 | `server/src/main/java/com/workforcehub/common/response/R.java` | 统一响应对象中定义了 `requestId` 字段，说明文档也把它视为标准返回结构的一部分，但当前 `ok/fail` 工厂方法都没有赋值，项目里也没有过滤器或上下文注入逻辑。这样接口文档与真实响应会长期不一致。 | 建议 | 增加请求链路 ID 生成与透传机制，例如在 Filter/Interceptor 中生成 `requestId`，写入 MDC 和请求上下文，再由 `R` 的工厂方法统一回填。 |

### 五、文档一致性

| 序号 | 问题位置 | 问题描述 | 严重程度 | 优化方案 |

### 七、优先处理建议

**第一优先级（进入业务开发前建议先处理）：**

1. **1-1** 修正 PostgreSQL 向量库迁移脚本语法，保证向量库可初始化
2. **2-1** 补最小安全链路，避免后续接口直接落入默认表单登录行为
3. **1-2** 明确 Flyway 与 Flowable 的改库边界，避免后续环境差异失控
4. **3-1** 收窄 Flowable 依赖范围，控制非必要引擎与表面扩张

**第二优先级（建议在第一轮基础设施整理时一并处理）：**

- **4-1** 打通 `requestId` 生成与回填链路
- **5-1** 修正文档与 DDL 统计口径，保证工程认知一致

## 第二部分：后端骨架成熟度评估

### 一、当前正向结论

- 工程骨架方向总体正确，已经建立了 `common + spi + 业务模块分包` 的基础结构。
- 统一响应、统一异常、状态枚举、线程池隔离、双库迁移目录等基础设施已经有了第一版落点。
- `spi` 层接口已经提前抽出，这对后续 `workflow ↔ agent`、`im ↔ agent` 解耦是正向信号。

### 二、当前核心风险判断

- 当前骨架还不能视为“基础设施已稳定”，至少数据库迁移、Security 行为、Flowable 边界这三处仍存在明显风险。
- 其中 PostgreSQL 迁移脚本语法错误属于可直接阻断初始化的问题。
- Security 与 Flowable 两处问题虽然暂时还没在业务代码里爆出来，但一旦开始接 Controller 和流程模块，就会快速放大成真实阻塞。

### 三、阶段性结论

当前后端骨架的**方向是对的**，但**基础设施边界还没有完全收口**。

更准确地说：

- 它已经具备继续演进的基础
- 但还不适合在当前状态下直接大规模铺开业务开发
- 更合适的顺序是先把这次审查指出的 4 个高优问题收掉，再继续推进认证、组织、流程、消息等业务模块

### 四、建议的下一步动作

1. 先修 PostgreSQL 向量库 DDL
2. 再补最小 Security API 骨架
3. 再收敛 Flowable 依赖与改库策略
4. 最后补 `requestId` 与文档统计口径

完成以上整理后，这份后端骨架才更适合作为后续业务开发的稳定基底。
