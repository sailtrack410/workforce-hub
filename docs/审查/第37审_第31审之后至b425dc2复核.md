## 第三部分：本轮新增正确性风险

| 序号 | 问题位置 | 问题描述 | 严重程度 | 优化方案 |
| --- | --- | --- | --- | --- |
| 2-1 | `FileLifecycleService.ensureUploaderOwnsAttachment`、`WorkflowRepository.createWorkflowAttachmentRef` | 员工文件回收站接口只校验 `uploader_type=USER` 且 `uploader_id=当前用户`，没有限制 `owner_type=PERSONAL_FILE`。workflow 克隆审批附件时又把 `WF_REQUEST` 附件的 `uploader_type/uploader_id` 设为申请人。结果申请人拿到审批附件引用 ID 后，可以通过个人文件删除、恢复、彻底删除接口操作审批归档附件；彻底删除还会释放个人和全局用量，但 `WF_REQUEST` 克隆本身没有计入个人用量，可能污染容量账本。 | 重要 | 员工文件生命周期入口必须限制 `owner_type=PERSONAL_FILE`；审批附件生命周期应只由 workflow 域按申请参与人和归档策略治理，不能复用个人文件删除语义。 |
| 2-2 | `WorkflowService.completeAgentPreReviewWithHumanApproval`、`WorkflowRepository.markHumanApprovalStarted` | Agent 通过或转人工回调先读 `PENDING_REVIEW`，再插入预审动作、启动 Flowable、无条件写入流程实例。这个流程没有对 `wf_request` 做条件抢占，也没有唯一幂等键。两个相同 Agent 回调并发进入时，都可能读到 `PENDING_REVIEW`，各自启动一个 Flowable 实例并生成多个待办，只是最后一个实例 ID 覆盖到申请头。 | 重要 | 回调处理前应通过条件更新或行锁抢占 `PENDING_REVIEW -> IN_APPROVAL/REJECTED`，并以 `request_id + agent_task_id + action_type` 建幂等保护；只有抢占成功的事务才能启动 Flowable。 |
| 2-3 | `WorkflowService.startHumanApproval`、`WorkflowTemplateVersionRow` | 模板发布时保存了 `flowable_definition_id`，但员工提交时读模型只取 `flowable_definition_key`，运行时用 `startProcessInstanceByKey` 启动最新 Key。若同一 Key 后续部署了新 BPMN，而业务模板版本仍指向旧定义 ID，历史发布版本会静默跑到新流程定义上，模板版本快照语义失效。 | 重要 | 已发布模板版本的运行时读模型应包含 `flowable_definition_id`，启动流程使用定义 ID 或明确记录“总是跟随最新 Key”的产品语义；如果保留版本治理，建议按定义 ID 启动。 |
| 2-4 | `WorkflowService.validateLeaveRequest`、`WorkflowRepository.insertLeaveDetail` | 服务只校验 `endAt > startAt` 和 `durationMinutes > 0`，没有校验请假时长是否与开始、结束时间一致，也没有服务端计算时长。后续 `module-leave` 扣减余额或 Agent 规则如果直接使用 `durationMinutes`，申请人可以提交跨整天时间但填较小分钟数绕过额度校验。 | 重要 | 服务端应统一计算或校验 `durationMinutes`，并明确工作时段、午休、节假日口径；余额扣减和 Agent 规则只能使用服务端可信时长。 |

## 第六部分：处理优先级建议

**第一优先级：修审批附件被个人文件生命周期接口误删的问题。**

- 这是跨模块权限边界问题，会直接破坏审批归档附件。
- 同时会带来用量释放口径错误。

**第二优先级：修 Agent 回调幂等和流程启动抢占。**

- Agent 后续如果有重试、超时补偿或消息重复投递，这个问题会从低概率并发变成常见边界。
- 建议在接正式 `module-agent` 前先补状态抢占和幂等键。

**第三优先级：固定 Flowable 定义版本和请假时长口径。**

- 模板版本治理已经保存定义 ID，运行时也应使用同一个快照。
- `module-leave` 扣减余额前必须把时长变成后端可信值。

**第四优先级：拆 workflow 大服务。**

- 当前 workflow 刚起步，拆分成本还低。
- 建议在接 `module-leave` 和多流程类型前先拆附件、任务、Agent 预审、查询几个边界。

## 第七部分：阶段性结论

第 31 审之后的提交整体方向是正确的：module-file 的清理补偿和临时对象泄漏问题已经收口，`FileCenterService` 也继续瘦身；module-workflow 已经形成可运行的后端最小闭环，并配套了较多集成测试。

但当前不建议把 workflow 直接推进到更复杂的业务联动前不处理上述风险。最需要先修的是审批附件生命周期权限边界和 Agent 回调幂等，这两项都属于“第一版功能看起来能跑，但一旦进入真实协作和重试场景就会破坏数据一致性”的问题。
